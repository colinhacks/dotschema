# dotschema: the plan

Import a JSON Schema in a `.schema.jsonc` or `.schema.json5` file and get the TypeScript type it describes plus a validator compiled by ajv: one npm package of a TypeScript 7.1 content mapper, a preload, and plugins for esbuild, Vite, webpack, Next.js and Jest, so the same import type-checks and runs in every host Motherload and Reylo run in. It is Motherload's schema loader, taken out of Motherload (`~/Documents/motherload`) on 2026-10-21; [DESIGN.md](./DESIGN.md) records every decision, most of them taken in Motherload, with their dates.

## Decisions

The maintainer's, Colin McDonnell, on 2026-10-21:

- **JSON Schema support leaves Motherload for a package of its own, dotschema:** "I'm trying to decide whether to extract the JSON schema into its own package, something like `dotschema`. I think it's cleaner to extract it personally. It's not really the same as the data loading that we do in the other stuff. Let's go ahead and do it. Put it into a new dir in Documents." It replaced the answer of earlier that day, "Keep it in `motherload`" ([DESIGN.md](./DESIGN.md#the-extraction-from-motherload)).
- **No documentation site:** "The new package doesn't need a documentation site. It can just have a README."
- **The hosts of dotschema's siblings, before the first release** (2026-10-25): "We need parity with the Reylo stuff", and "I also have a starter kit now for implementing content mappers that should include a similar baseline." So dotschema runs where Reylo, Motherload and the content-mapper starter kit run: Node, Bun, nub, Vite, Vitest, Rollup, Rolldown, esbuild, webpack, Rspack, Next.js with Turbopack and with webpack, Jest and Cloudflare Workers, through Motherload's adapters ([DESIGN.md](./DESIGN.md#the-hosts)).
- **Dependencies in generous ranges** (2026-10-26): "I believe we decided to just have a regular dependency on AJV, not a peer dependency, so that we could swap out our own parsing engine later. But we should make the version ranges that are accepted as generous as possible to avoid duplication for the package managers that do that sort of thing." So each of ajv, json5 and jsonc-parser is a caret range on the oldest version that passes the checks, `^8.11.0`, `^2.2.2` and `^3.1.0`, and none spans an older major, under which a schema gave a different module ([DESIGN.md](./DESIGN.md#packaging)); ajv-formats, `^3.0.1` that morning, is no dependency since the formats became dotschema's own the same day (below).
- **dotschema's own formats** (2026-10-26): asked "Which format work should dotschema build now?", the maintainer ticked all three options: "Fix the standard formats the test suite catches: date-time, time, duration and uuid as dotschema's own copies; the rest of ajv-formats unchanged"; "Add Zod's formats: jwt, credit_card and iban with Zod's own checks, plus Zod's regex formats for schemas written by hand"; and "Add the IDN and IRI formats: idn-email, idn-hostname, iri, iri-reference". So each format checked by a function is a file of dotschema's own, which a module inlines only when it uses it, and ajv-formats is no dependency ([DESIGN.md](./DESIGN.md#formats)).
- **Zod's JSON Schema output stays Zod's** (2026-10-26): "Leave Zod as it is." Where `z.toJSONSchema` emits a standard format whose meaning differs from Zod's own check (`z.email()`, `z.url()`, `z.httpUrl()`, `z.ipv6()`, `z.iso.duration()`), the difference is Zod's to fix, or not, and dotschema keeps each standard format's standard meaning ([DESIGN.md](./DESIGN.md#formats)).
- **Motherload does not depend on dotschema, for now:** "We could always add support into Motherload later and give Motherload a dependency on dotschema, but not right now." The two meet in one project through the protocol Motherload's loaders already share, its global keys kept ([DESIGN.md](./DESIGN.md#the-shared-protocol)).

Taken in Motherload, and carried here as they were:

- **A schema file is a schema, not data** (2026-10-03): it becomes its TypeScript type plus a validator, compiled by ajv when the module is built, so a bundle holds no validator library ([DESIGN.md](./DESIGN.md#the-validator)).
- **The types come from an emitter of the package's own** (2026-10-09, `src/schema-types.ts`), not json-schema-to-typescript (15.9 MB with prettier) or json-schema-to-ts (the type computed again in every type check), so typing a schema needs nothing installed ([DESIGN.md](./DESIGN.md#the-types)).
- **ajv is a dependency, not a peer** (2026-10-20): "because then later on we could move away from AJV without breaking people." The maintainer is interested in a validator of the package's own in ajv's place, "owning this top to bottom, having it be self-contained" ([Open](#open)).
- **A schema file's suffix is `.schema.jsonc` or `.schema.json5`,** not `.schema.json`: TypeScript nightlies after 2026-10-13, and the 7.1 beta branch, refuse a content mapper extension that ends in `.json` (microsoft/TypeScript#64581, TS18066). The answer of 2026-10-19 was `.jsonschema`; on 2026-10-20 the maintainer chose `.schema.jsonc` instead, and then `.schema.json5` beside it: "I think we can continue supporting it for .schema.jsonc and .schema.json5. Kind of nice to be able to have comments as well." The suffix names the dialect. The docs document `.schema.jsonc`, with `.schema.json5` in a one-line note ("the docs should only document .schema.jsonc", then "document that json5 is supported, but do it in a one-liner in a callout") ([DESIGN.md](./DESIGN.md#the-suffix)).
- **A file is a schema by its suffix alone,** never by its content (2026-10-21, "By the suffix alone, as now") ([DESIGN.md](./DESIGN.md#the-suffix)).
- **A schema module is a Standard JSON Schema too,** for the `"draft-07"` and `"draft-2020-12"` targets (2026-10-20, "Yes, draft-07 and 2020-12"): `~standard.jsonSchema.input` and `.output` give the schema as one self-contained JSON Schema in the target's draft, every other file it reaches folded in, and throw for another target or a keyword the target cannot express ([DESIGN.md](./DESIGN.md#standard-json-schema)).
- **A schema's `$ref` to another file is followed** (2026-10-20): "We absolutely need to follow refs into other files." The type is imported from the other file's module and the validator is compiled from every file the schema reaches ([DESIGN.md](./DESIGN.md#references-to-other-files)); a `$ref` to a URL is not followed ([Open](#open)).
- **A keyword a schema's draft does not define is ignored,** by the validator and by the type (2026-10-20): "I want to make sure that any unrecognized keywords that show up inside the JSON schema file are ignored. That's technically valid, but I want to say that sometimes AJV is overly strict with this." That covers another draft's keywords and the ones ajv adds, `$async` and OpenAPI 3.0's `nullable` among them ([DESIGN.md](./DESIGN.md#the-validator)).
- **An `if`/`then`/`else` that tests a property's value is typed as a union that narrows** (2026-10-20), picked over draft-04 support: "I don't care about draft 4 support right now" ([DESIGN.md](./DESIGN.md#the-types)).
- **A schema module has `.validate()` and `.is()`, and nothing on it throws** (2026-10-20): "We should not provide any method that throws an error." The `.validate()` method returns every issue (ajv with `allErrors`), each `{ message, path, keyword }`, or the value it was given; `.is()` is a type guard backed by a second validator that stops at the first failure; `.parse()`, which threw, is gone. The maintainer asked for it written up as a TypeScript interface, and answered "Build it as written". On the issue's other fields, ajv's `params` and `schemaPath`: "Drop both". For a `oneOf` whose variants a property tells apart, the maintainer picked reporting only the matching variant's issues (ajv's discriminator, added to the copy ajv compiles); and for ajv's first-failure validator passing `[]` for `contains` beside a tuple, a guard in `.is()`: "Do option B, but this is something that we should make a note of for when we eventually vendor AJV" ([DESIGN.md](./DESIGN.md#the-validator)).
- **A schema's type has complete fidelity with what the schema allows** (2026-10-20): "It should have complete fidelity with what is allowed by the JSON schema itself." So a schema without `type` is typed with every JSON value its keywords leave open, and the validator checks the schema as written, no stricter ([DESIGN.md](./DESIGN.md#the-types)).
- **A hover shows a schema's properties** (2026-10-26): "in general, I think we want to show the actual raw type, not an interface or anything that's not very informative. People want to see the actual properties for visibility." So the value `.validate()` returns or `.is()` narrows prints the root's properties, and a `$ref` among them prints the name of what it points to ([DESIGN.md](./DESIGN.md#the-types)).
- **The type is `user.Type`** (2026-10-26): "I think I'm okay having the inferred type just be called `Type`. ... I think the default import should have a `.Type` property on it. That should be the recommended way to access it." The module exports the root only as `Type`, and the default import carries it as `.Type`; a `$ref`'d root prints by its file's name, `User`, which nothing exports ([DESIGN.md](./DESIGN.md#the-types)).
- **A `/** */` comment is a doc comment** (2026-10-26): offered the options, the maintainer picked "Only /** */ comments — a /** */ comment above a property becomes its JSDoc where it has no description; // stays a private note, as in TypeScript". So a `/** */` comment before a property's key, a definition's key or the root is its JSDoc in the types, in JSONC and JSON5, and a `description` wins over it ([DESIGN.md](./DESIGN.md#the-types)).
- **Each definition is a validator of its own** (2026-10-26), the fragments item: the maintainer asked to "add support for fragments, like we basically want to resolve refs if we don't already, obviously. I feel like when you import a file, you want to see all the top-level properties of that, but then if there is a ref, that kind of gives you permission to represent that referenced type by name, in which case you should obviously...", and offered the options, picked "Each $defs entry importable as its own validator — import { address } from "./user.schema.jsonc", with address.validate() and address.is()". So each entry of the root's `$defs` or `definitions` is a named export, its key in camelCase, with the module's own surface and its type as `address.Type`, which a bundler leaves out when nothing imports it. A `$ref` with a fragment (`./user.schema.jsonc#/$defs/address`) was followed already, the definition printing by its name and any other pointer inlined, and since the same day one to an anchor (`./user.schema.jsonc#city`) is too, by the same rules, while a fragment that points to nothing or to a value that is not a schema is a problem at the `$ref` ([DESIGN.md](./DESIGN.md#each-definition-a-validator), [references](./DESIGN.md#references-to-other-files)).
- **Pick and omit are methods** (2026-10-26): the maintainer had raised it that day ("I do think we also need to consider some ideas around letting people pick and omit. That's one of the biggest missing things, I feel, from the JSON schema vocabulary, and it's going to be a problem here."), and picked "Methods in TypeScript — user.pick("id", "name") and user.omit("id"), as in Zod, each giving a new schema at run time", told that "validators are compiled at build time, so a subset chosen at run time needs every property's validator compiled separately and joined at run time, or ajv shipped at run time, which dotschema avoids today". So a root or definition that is a plain object has `.pick()` and `.omit()`, which give the schema whose `properties` and `required` keep the keys chosen, validated by each property's validator, compiled with the module, joined at run time with ajv's object checks; ajv is not shipped ([DESIGN.md](./DESIGN.md#pick-and-omit)).
- **Every module is an ES module,** whatever the nearest `package.json` says (2026-10-20): "I definitely have a strong preference for going ESM first here." The mapper reports `.mts` ([DESIGN.md](./DESIGN.md#the-mapper-process)).

## Names

On npm, `dotschema` is held by the maintainer as a 0.0.0 placeholder (Motherload's PLAN.md, "Names"), so the first release is 0.0.1. In prose the product is dotschema, lowercase, as dotsql is; `dotschema` in code is the package, the import specifier, the diagnostic source and the Standard Schema vendor.

## What works

Run `nub install`, then `nub run typecheck` and `nub run test`. The suite holds every schema test Motherload had at d21b5ac, type-checks [lab/basic](./lab/basic) through the content mapper with exact-type assertions and a failing control, checks diagnostics placed in broken schema files, runs `lab/basic` under the preload and bundles it with the esbuild plugin into a file that imports nothing, and checks that dotschema and a stand-in for Motherload's `.jsonc` loader defer to each other in Node, Bun, esbuild, webpack, Rspack, Vite, Rollup, Rolldown and Next.js's config. Each host has a lab with its own dependencies, installed with `nub install` in it: `lab/bundlers` (webpack, Rspack, Vite for Node and the browser, Rollup, Rolldown), `lab/nextjs` (Turbopack and webpack), `lab/jest` (Jest and Vitest) and `lab/cloudflare` (a Worker in workerd), with `lab/nub` and `lab/bun` needing only nub and Bun; their tests are skipped where they are not installed. On 2026-10-25, with every lab installed, the suite was 137 tests, 129 passing and the 8 of `tests/motherload.test.ts` skipped; with `MOTHERLOAD_DIR` naming a Motherload checkout with its dependencies installed, those run too, beside the real Motherload in every host, and all 137 passed against Motherload's `main` at 099d7e2. Running `nub run build` writes the package to `dist/dotschema`, and `nub run check-dist` installs it from a tarball outside the repository into seven projects, the host labs among them, and runs each host there. On GitHub, `.github/workflows/test.yml` installs the labs and Bun and runs those four on every push to `main`. [AGENTS.md](./AGENTS.md) lists the layout.

## Steps

1. **The extraction** (done on 2026-10-21): the schema loader, its tests, its fixtures and `lab/basic`'s schemas from Motherload's commit d21b5ac, with the pieces of `@motherload/core` they use copied in, every user-facing name changed to dotschema's, and Motherload's protocol for loaders in one host kept ([DESIGN.md](./DESIGN.md#the-extraction-from-motherload)).
2. **A repository on GitHub and a release** (done on 2026-10-26): the repository is public at colinhacks/dotschema since 2026-10-21, with its release workflow, Motherload's for one package, and its two GitHub environments ([DESIGN.md](./DESIGN.md#releasing)). The maintainer configured the trusted publisher with `bash scripts/npm-first-publish.sh` on 2026-10-26, and 0.0.1 was released the same day from b28c1ca by `release.yml` (run 40424054480): staged, approved on npm through `stager`, served by npm as `latest` with the caret ranges in its manifest, then tagged `v0.0.1` with its GitHub release.
3. **Every host of dotschema's siblings** (done on 2026-10-25, the maintainer's "We need parity with the Reylo stuff"): `dotschema/vite` for Vite, Vitest, Rollup, Rolldown and Cloudflare Workers, `dotschema/webpack` and `dotschema/turbopack` for webpack, Rspack and Turbopack, `withDotschema` from `dotschema/next`, and `dotschema/jest`, on Motherload's adapters at 099d7e2, each with a lab that runs it, and nub's and Bun's preloads with labs of their own ([DESIGN.md](./DESIGN.md#the-hosts)). Verified that day: `nub run typecheck`; `nub run test`, 137 tests with every lab installed, 8 skipped without `MOTHERLOAD_DIR` and none with it; `nub run build` and `nub run check-dist`, seven projects; and by hand, `next build` failing on a type error under both bundlers, and wrangler's own bundler and workerd's refusal of `new Function` ([DESIGN.md](./DESIGN.md#cloudflare-workers)).
4. **dotschema's own formats** (2026-10-26, the maintainer's three options, [Decisions](#decisions)): the formats are files of dotschema's own, a module carrying only those it uses, and ajv-formats is no dependency; `date-time`, `time`, `duration` and `uuid` pass the JSON Schema Test Suite, ajv-formats' other formats are unchanged ([DESIGN.md](./DESIGN.md#formats)). Zod's formats, and the IDN and IRI formats, are next.

## Open

- **Motherload and schemas:** Motherload 0.0.1 still reads `.schema.jsonc` and `.schema.json5` itself, and beside it the two loaders tie in a runtime and the host's order decides (measured, [DESIGN.md](./DESIGN.md#the-shared-protocol)). Motherload 0.1.0, published the same day, 2026-10-21, has no schema loader (Motherload's commit 1e3fad2), which removes the tie for 0.1.0 and later. Whether Motherload later depends on dotschema is the maintainer's "not right now".
- **The shared keys:** the protocol's global keys are `Symbol.for("motherload.registered")` and `Symbol.for("motherload.plugin")`. Neutral names would need both packages to change together, and to read the old keys too while older versions are installed; whether that is worth doing is open.
- **The copied core:** `src/core/` is a copy of part of `@motherload/core` at d21b5ac, its webpack, Vite and Jest adapters at 099d7e2, with dotschema's change to the webpack loader for Rspack, to `utf8Range`, which keeps a diagnostic's range within the file (2026-10-26: a syntax error at the end of a file was TS18069 in place of the error, [DESIGN.md](./DESIGN.md#diagnostics)), and to the Vite plugin, whose module is Vitest's cache key and whose `watchChange` tells Vitest of a change to a file a module was made from (2026-10-26: a schema whose `$ref`'d file changed came back stale from Vitest's cache, [DESIGN.md](./DESIGN.md#the-vite-plugin)); Motherload had both faults, reproduced and fixed on its `main` the same day by the thread the maintainer asked for ("Open a Motherload thread"): its commit 5e3af83 clamps `utf8Range` as dotschema's 1c675c1 does (a cut-off `.toml`, `.yaml`, `.jsonc` or `.json5` and an empty `.jsonc` or `.json5` each gave TS18069, and after five TS18070 turned the mapper off), and 9ee97e4 carries dotschema's `configureVitest` and `watchChange` line for line (no Motherload format sets `watchFiles`, but under nub's layout Vitest found no lockfile and kept a loader's first output across runs), so dotschema's copy and Motherload's agree again on both, without a change to the shared protocol. A fix to Motherload's adapters (a host's quirk, a protocol change) has to be made here too; nothing checks that the two stay in step but the interop tests.
- **The validator:** ajv is the maintainer's choice and is built in; whether to accept others (a Standard Schema validator generated by another library). The maintainer is interested in a validator compiler of the package's own in ajv's place, which ajv as a dependency rather than a peer leaves room for; whether and when to build one is open. When ajv is vendored or replaced, fix at the source the bug `.is()` guards against: ajv 8.20.0's validator without `allErrors` passes `[]` for `contains` beside a tuple, so `.is()` confirms a pass with the `allErrors` validator wherever that shape occurs; the guard (`needsConfirmation` in `src/schema.ts`) can then go ([DESIGN.md](./DESIGN.md#the-validator)).
- **A `$ref` to a URL** (`https:`, `urn:`): not followed; ajv reports it and its type is `unknown`. Following a URL needs a fetch when the module is built, or a map from URLs to files in the project; which, if either, is open.
- **The editor and a change to a referenced file** (measured on 2026-10-25 with the 7.1.0-beta language server, not fixed): after `user.schema.jsonc` changed, a schema that reaches it by import (`team.schema.jsonc`'s `$ref` to its root) was re-typed, but one that inlines a pointer into it (`{ "$ref": "./user.schema.jsonc#/properties/role" }`) kept its old type until that schema itself was edited or the server restarted, since the server runs the mapper again on the changed file alone; `tsc --watch` on the same version re-types it ([DESIGN.md](./DESIGN.md#the-editor)). Whether to emit an inlined pointer as an import instead, or to ask TypeScript for a mapper's dependencies, is open.
- **Draft-04:** refused, in the type check and the build. ajv validates it only through `ajv-draft-04` (1.0.0, 2021-05-23, a peer of `ajv` ^8.5.0; not tried). The maintainer, on 2026-10-20: "I don't care about draft 4 support right now." Draft-03 and OpenAPI 3.1's dialect are refused too.
- **Shared schemas in a bundle:** each schema module carries its own compiled copy of every file it refers to, and of the file of each format it checks with a function (`date-time`), where until 2026-10-26 it carried ajv-formats' whole formats module ([DESIGN.md](./DESIGN.md#formats)); ten modules sharing one schema bundled to 188 KB minified, 6.3 KB gzipped (measured in Motherload, [DESIGN.md](./DESIGN.md#references-to-other-files)). Sharing needs a module to import the modules of the files it refers to and call their validators, which ajv's standalone code cannot link; a validator compiler of the package's own (above) could emit modules that way.
- **The TypeScript nightly:** the repository pins `7.1.0-dev.20261002.1`, as Motherload does, and the README installs `typescript@beta`, as Motherload's does. On 2026-10-25 a copy of `lab/basic` installed from the tarball type-checked on `7.1.0-beta`, and its language server typed the schemas ([DESIGN.md](./DESIGN.md#the-editor)); `nub run check-dist` with that version, and with `7.1.0-dev.20261024.1`, passed in the coordinator's run of that day, before the host labs. Whether the repository moves its pin to the beta is open.
- **Motherload's webpack loader under Rspack:** Rspack loads a loader only when its turn comes, so Motherload's `.jsonc` loader, running first, cannot see dotschema's mark when dotschema's rule comes first, and makes a data module of the schema; dotschema's loader now reads the file itself there, so both orders work against Motherload's `main` at 099d7e2 ([DESIGN.md](./DESIGN.md#the-webpack-loader)). On Motherload's side, its loader as the weaker one could find a sibling not yet loaded by its path, and its own Rspack test passes only because its stand-in for dotschema ignores what it is handed. Neither is written here: Motherload is read, not written.
- **The floors in CI:** `test.yml` runs `nub run check-dist --lowest`, every host at the floor of each range from the tarball, but the repository's own tests, where the tests that hold the floors live, run at the lockfile's versions, the newest. They ran at the floors by hand on 2026-10-26, through an `overrides` field in `package.json` ([DESIGN.md](./DESIGN.md#packaging)); whether a CI job should do the same, and whether `release.yml`'s test job should run `--lowest` too, is open.
- **A previous major in a range:** json5 1.0.2 passes every test but the one written to hold its floor, and is widely installed; a range over it (`^1.0.2 || ^2.2.2`) would share more copies, and refuse an unquoted key from Unicode 10 depending on the copy a project's install picked ([DESIGN.md](./DESIGN.md#packaging)). Kept out on 2026-10-26, as ajv-formats 2 was, which is no dependency since the formats became dotschema's own the same day; whether that trade is the maintainer's to change is open.
- **Example projects:** Motherload and Reylo keep a complete project per setup in `examples/`, for their docs' agent prompt; dotschema has labs, which run each host on `lab/basic`'s schemas, and no examples, docs site or agent prompt. Whether it wants them is the maintainer's.
