# dotschema: design record

Each section is one decision: what was decided, the alternatives weighed, and the evidence. Most were taken in Motherload (`~/Documents/motherload`), whose schema loader dotschema is, extracted on 2026-10-21 ([below](#the-extraction-from-motherload)); their dates and the maintainer's words are kept as Motherload's DESIGN.md recorded them at commit d21b5ac, and a path names this repository's file unless it says Motherload's. "Measured" means a command was run and its output read, in Motherload's repository or in a scratch directory before the extraction, and in this one after; measurements were taken on macOS with Node v26.10.0 and nub v0.9.5 in Motherload, and with Node v26.11.1 and nub v0.9.6 here.

## The extraction from Motherload

The maintainer's decision of 2026-10-21: "I'm trying to decide whether to extract the JSON schema into its own package, something like `dotschema`. I think it's cleaner to extract it personally. It's not really the same as the data loading that we do in the other stuff. Let's go ahead and do it. Put it into a new dir in Documents." Then: "The new package doesn't need a documentation site. It can just have a README." And: "We could always add support into Motherload later and give Motherload a dependency on dotschema, but not right now." Earlier the same day, asked whether to take schemas out of `motherload` before its first release, the maintainer had answered "Keep it in `motherload`"; Motherload's DESIGN.md (Packaging) records that answer and what was measured for it: the schema package was 1,828 of the 2,708 lines of package source and its four test files 1,626 of the 2,306 lines of tests, and ajv and ajv-formats were about 1.09 MB of `motherload`'s install.

- **One package, `dotschema`, at the repository's root,** as `motherload` is Motherload's root package: the content mapper (`typescript.contentMapper` in `package.json`), the preload (`dotschema/register`), the esbuild plugin (`dotschema/esbuild`) and the types (`dotschema`). The extensions are Motherload's, `.schema.jsonc` and `.schema.json5`. npm held a 0.0.0 placeholder of `dotschema`, the maintainer's (Motherload's PLAN.md, "Names"), so the first version is 0.0.1.
- **Taken from Motherload's commit d21b5ac,** not from its working tree: `packages/schema/src/` (the module, the emitter, the references, the Standard JSON Schema conversion, the loader and its entry points, the types), the schema tests (`tests/schema.test.ts`, `tests/schema-types.test.ts`, `tests/json-schema.test.ts`, `tests/verdicts.test.ts`, and the schema parts of `tests/lab.test.ts`, `tests/packages.test.ts`, `tests/adapters.test.ts` and `tests/mapper.test.ts`), the fixtures (`tests/fixtures/json-schema/`, `tests/fixtures/declaration/`, the schema files of `tests/fixtures/errors/`), `lab/basic`'s schema files, and the build and its check (`scripts/build.ts`, `scripts/check-dist.ts`).
- **Self-contained: the pieces of `@motherload/core` the schema code uses are copied into `src/core/`,** and the two parsers it reads a schema with into `src/parse.ts`, so the package depends on ajv, ajv-formats, jsonc-parser and json5 alone (and on ajv-formats no longer since 2026-10-26, when the formats became dotschema's own, [below](#formats)). A dependency on `@motherload/core` was the alternative: it reports every diagnostic as `motherload` (`DIAGNOSTIC_SOURCE` in its `universal.ts`), its messages name Motherload, and the Motherload packages move together at one version (Motherload's DESIGN.md, Packaging), so each Motherload release would be a dotschema dependency to move. The copy is small and changes rarely: of core's files, `src/core/universal.ts` (the loader contract and the hosts' adapters, with dotschema's diagnostic source and option message, and since 2026-10-25 the webpack, Vite and Jest adapters and the Bun branch of the esbuild plugin from Motherload's 099d7e2, with two changes of dotschema's, one for Rspack, [below](#the-webpack-loader), and a diagnostic's range kept within the file, [below](#diagnostics)) and `src/core/rpc.ts` (the JSON-RPC server, unchanged) are whole; `src/core/serialize.ts` keeps `Value`, `propertyName`, `toJs` and `literal`, without the check that a value is one a module can carry (`assertValue`, `UnsupportedValue`), since a JSONC or JSON5 file holds nothing else (measured: json5 2.2.3 defines a `__proto__` key as an own property, and jsonc-parser's tree is read into plain objects); `src/core/problems.ts` keeps `Problem`, `Parsed`, `CODES`, `offsetOf` and `fail`, without `carry` and `BOM`; and `src/core/standalone.ts` is `combine` and `standalone` from `module.ts` for one loader, without `moduleLoader`, `valueModule` and the data module's types. Motherload's `parseJsoncFile` and `parseJson5File` are copied without `carry`, and `parseSchemaFile` moved beside them from `refs.ts`.
- **Every name a user sees is dotschema's:** the diagnostic source (`dotschema4`, not `motherload4`), the Standard Schema `vendor`, the package the generated types import `Schema` from, the loader's and the esbuild plugin's name (which a load error starts with), the message for an extension the package does not read ("dotschema reads .schema.jsonc and .schema.json5 files; …"), the option message, the message for a missing ajv ("a dependency of dotschema … reinstall dotschema"), the `$id` and Standard JSON Schema messages, the id each file gets inside ajv (`dotschema:<n>`), and the import's local name in the generated types (`__DotschemaSchema`). The diagnostic codes keep Motherload's numbers, so `dotschema4` is a schema problem as `motherload4` was; 2, a value no module can carry, has no case here.
- **The schema loader takes no `typesFrom`:** in Motherload `schemaLoader(typesFrom)` let `motherload` and `@motherload/schema` each name itself as the package the types import from; here the types always import from `dotschema`.
- **Motherload's protocol for loaders in one host is kept as it is,** global keys included, so that Motherload's `.jsonc` and `.json5` loaders and dotschema defer to each other by the longer suffix ([below](#the-shared-protocol)).
- **Not carried over:** the docs site (the maintainer: "It can just have a README"; dotschema has one of its own since 2026-10-27, [below](#the-docs-site)), the release workflow and its scripts at first (`.github/`, `scripts/bump.ts`, `scripts/npm-first-publish.sh`), which needed the GitHub repository; they followed it the same day, adapted to one package ([below](#releasing)), and `lab/packages`, a schema package beside a `.jsonc` package, whose place the interop tests take (`tests/interop.test.ts`, `tests/motherload.test.ts`).

## The shared protocol

A runtime or a bundler does not route by the longest suffix as TypeScript does: Node runs the hook registered last first, and esbuild runs plugins in their order, so Motherload's `.jsonc` loader would read `user.schema.jsonc` as data, its validator gone, for one order of the flags (Motherload's DESIGN.md, Packaging, "The longest suffix, in every host"). Motherload solved it among its own packages with a protocol in `@motherload/core`'s `universal.ts`, and dotschema speaks the same one (`src/core/universal.ts`), so a project can use Motherload for its data and dotschema for its schemas in any order.

- **A loader** is an object `{ name, extensions, filter, load, types }`: `extensions` the suffixes it reads, `filter` a RegExp of every path it takes, and `load(source, path)` the module's JavaScript, `{ code, problems, watchFiles? }`.
- **A claim** is the length of the longest of a loader's extensions that ends the path, 1 for a path its filter takes by name alone, 0 for one it does not take (`claim`); a loader is outranked on a path when another claims it more strongly (`outranked`), and the strongest, the first on a tie, owns it (`ownerOf`).
- **Node and Bun:** each preload adds its loader to the set at `globalThis[Symbol.for("motherload.registered")]` before it registers its hook, so the set holds every Motherload and dotschema loader in the process. A Node hook passes a file another loader in the set outranks it on to the next hook; a Bun plugin, which may not return nothing (oven-sh/bun#5303), loads it with the loader that owns it.
- **esbuild:** each plugin object carries its loader under `Symbol.for("motherload.plugin")`; a plugin finds its siblings in `build.initialOptions.plugins` and returns nothing for a file a sibling outranks it on.
- **webpack and Rspack:** each loader's function carries its loader under the same key, and a loader finds its siblings among the loaders on the resource (`this.loaders`, each function as `normal`); every rule that matches a file runs, and a loader passes on, as it came, a file a sibling outranks it on. Rspack loads a loader only when its turn comes, so there dotschema's loader reads the file itself where a loader it outranks is on the file ([below](#the-webpack-loader)).
- **Vite, Rollup and Rolldown:** each plugin object carries its loader under the same key; a plugin finds its siblings in Vite's resolved plugins (`configResolved`) or in Rollup's and Rolldown's input options (`options`), and returns `null` for a file a sibling outranks it on.
- **Turbopack and Jest run one rule per file,** the first that matches, so there the order decides and no loader can defer: `withDotschema` puts its Turbopack rule first ([below](#nextjs)), and a Jest config lists dotschema's pattern before a `.jsonc` or `.json5` one ([below](#the-jest-transformer)).
- **The keys stay Motherload's,** `motherload.registered` and `motherload.plugin`: Motherload 0.0.1, published on 2026-10-21 (Motherload's commit 61c1c55), uses them, and a dotschema of its own keys would not see its loaders, nor they dotschema's. Measured with dotschema's keys changed to `dotschema.registered` and `dotschema.plugin`: `tests/interop.test.ts` failed in Node, Bun and esbuild. Either package changing the keys, the loader's shape or the rule breaks the other, so a change is made in both.
- **A tie defers to neither:** two loaders that claim one suffix, such as Motherload 0.0.1 (which reads `.schema.jsonc` itself) beside dotschema, are left to the host's order. Measured on 2026-10-21 against the Motherload checkout at its `main` (61c1c55), with `motherload` for `.jsonc` and `.json5` and dotschema for the schema suffixes: the type check passed through both mappers, since TypeScript gives the schema files to the entry with the longer suffix, and `--import motherload/register --import dotschema/register` loaded the schemas with dotschema, while the other order loaded them with Motherload's own schema loader (vendor `motherload`). Against the Motherload worktree whose schema loader was being removed, the same test passed in every order, and on 2026-10-25 it passed against Motherload's `main` at 099d7e2, after Motherload 0.1.0 shipped without its schema loader.
- **Tested** against a stand-in for Motherload's `.jsonc` loader written against the protocol alone (`tests/standin.ts`, which mirrors Motherload's adapters and `withMotherload` at 099d7e2): in Node with both preloads in each order, in Bun with dotschema's preload adding its loader where the stand-in's plugin finds it, in esbuild, Vite, Rollup and Rolldown with both plugins in each order, in webpack and Rspack with both rules in each order, and in Next.js's config with both wrappers in each order (`tests/interop.test.ts`), and in Jest with dotschema's pattern first (`lab/jest/jest.interop.config.cjs`); and against a real Motherload checkout when `MOTHERLOAD_DIR` names one (`tests/motherload.test.ts`, skipped otherwise): a project typed through both mappers, run under both preloads, bundled with both esbuild plugins, both webpack loaders (webpack and Rspack) and both Vite plugins (Vite, Rollup and Rolldown) in each order, tested with both Jest transformers, and `withMotherload` composed with `withDotschema` in each order. All passed on 2026-10-25 against Motherload's `main` at 099d7e2.

## The types

A `.schema.jsonc` or `.schema.json5` file (`.schema.json` until 2026-10-19, [below](#the-suffix)) becomes the type the schema describes plus a validator (the maintainer's decision). The types come from an emitter of its own, `src/schema-types.ts` (the maintainer's decision of 2026-10-09, taken in Motherload). The alternatives were json-schema-to-typescript 16.0.0 (2026-08-28, 5.1 M weekly downloads), which compiles a schema to TypeScript declarations but installs 15.9 MB with its dependencies, prettier 9.96 MB of it, loaded every time ([Packaging](#packaging)); and json-schema-to-ts 3.1.1 (47 M weekly downloads, last release 2024-08-29, 0.47 MB with `@babel/runtime` and `ts-algebra`), which infers the type from the schema as a literal type, so the checker computes it again in every type check and each `$ref` is inlined.

- **No dependency:** the emitter is part of dotschema and needs nothing installed; only the validator needs ajv.
- **The module exports the root as `Type`,** whatever the root `title`, and the default import names it as `user.Type`; the name it is declared under, and why, are [below](#the-types) ("A hover prints a value's properties"). An object root is an `interface`, any other root a `type`.
- **Each definition is a named type:** every entry of the root's `$defs` (or draft-07 `definitions`) is exported under its key in PascalCase (`my-tag` is `MyTag`; `Type2` when the name is taken), and a `$ref` to it is that name, so a recursive schema stays finite. The pointer `#` is the root's name ([below](#the-types)); a pointer to anything else in the schema is inlined, and is `unknown` when it leads back into itself. A `$ref` to an anchor, an `$anchor`, a `$dynamicAnchor` or draft-07's plain-name `$id` (`"#name"`), follows the same rules by where the anchor is declared, in the file or in another ([below](#references-to-other-files)); until 2026-10-26 its type was `unknown`, though ajv validated it. Each is a validator too, exported under its key in camelCase ([below](#each-definition-a-validator)).
- **A hover prints a value's properties, and a `$ref` within them by name,** the maintainer's direction of 2026-10-26: "in general, I think we want to show the actual raw type, not an interface or anything that's not very informative. People want to see the actual properties for visibility." The root is declared under its file's name in PascalCase (`user.schema.jsonc` declares `User`), named after the definitions so that a definition keeps its key's name (a `tag.schema.jsonc` whose `$defs` has `tag` declares the definition `Tag` and the root `Tag2`), and is not exported under that name: the module exports it as `Type`, by `export type { User as Type }`, and the default import names it as `user.Type`, through `declare namespace schema { export type { User as Type }; }`, a namespace of types alone that merges with the default export's const. That is the maintainer's choice of the same day: "I think I'm okay having the inferred type just be called `Type`. ... I get that it's kind of anonymous in the imports right now, and I think that's good. If you do a default import, there should still be a way to refer to the type. I think the default import should have a `.Type` property on it. That should be the recommended way to access it." The default export's type writes the root's type out, `Schema<{ … }, Json>`, so a hover over the value `.validate()` returns or `.is()` narrows prints the schema's properties, while a `$ref` among them prints the name of what it points to: another file's root, imported as its `Type`, by the root's own name (`User`), or as `user.Type` in a file that imports that module, as TypeScript prints a type by the name it has where the hover is; a definition by its own name. Measured on 2026-10-26 with the 7.1.0-beta language server, at the hover's first level: a team narrowed by `.is()` was `Type` and its `lead` `Type`; they are `{ name: string; lead: User; members: User[]; office?: Address | undefined; }` and `User` in a file that imports only the team's module, and `lead: user.Type` in one that imports the user's as well. A `type Type = User` alias in place of the re-export was measured and refused: imported by another file, it made the hover print `Type`. A file that names the type on import (`import type { Type as Member }`) has its hovers print `Member`. A library's declarations write the root out as well (`tests/fixtures/declaration`). The alternatives: exporting the root under its file's name as well, which the maintainer's "anonymous" leaves out; the schema's `title`, which not every schema has and which can be prose ("A user of the app"); an option of the content mapper ("This could be configurable in the content mapper options"); and declaring the root as `Type`, which every root printed as.
- **The keywords it reads:** `type` (one or a list), `properties` and `required` (an optional property is `a?: T`, and `a?: T | undefined` in a project with `exactOptionalPropertyTypes`, below; a required key that `properties` does not list has the type of the `patternProperties` whose pattern matches it, or of `additionalProperties` when none does, [below](#the-types)), `additionalProperties`, `patternProperties` and `unevaluatedProperties: false` (an index signature, which also covers the named properties, as TypeScript requires, or none when closed; `unevaluatedProperties` closes the object only when no keyword beside it can allow another key: `allOf`, `anyOf`, `oneOf`, `if`/`then`/`else`, `dependentSchemas` or a `$ref`), `items`, `prefixItems`, `additionalItems` and `minItems` (an array, or a tuple whose positions from `minItems` on are optional), `const` and `enum` (literal types), `allOf` (an intersection), `anyOf` and `oneOf` (a union), `if`/`then`/`else` that test a property's listed values (a union, [below](#the-types)), and `description` (a doc comment, as is a `/** */` comment before a key that has none, [below](#the-types)). A keyword the schema's draft does not define is not read, `nullable` among them ([below](#the-validator)). Without `type`, the object keywords constrain an object and the array keywords an array, and every other JSON value passes them, so the type is that object or array or any other JSON value (`{ "properties": { "a": { "type": "string" } } }` is `{ a?: string | undefined; ... } | unknown[] | string | number | boolean | null`), the maintainer's answer of 2026-10-20: "It should have complete fidelity with what is allowed by the JSON schema itself." Until then such a schema was an object alone, though the validator accepted `5`. The JSON types a value can have come from `type`, `const`, `enum`, `allOf`, `anyOf`, `oneOf` and `$ref`, and a member of `allOf`, `anyOf` or `oneOf`, or a `then` or `else` read as an object, is read within its schema's: `{ "type": "object", "allOf": [{ "properties": ... }] }` is an object and that object, not a union of every JSON type. A schema should declare `"type": "object"` where it means one. A keyword that narrows a value no TypeScript type can express (`minLength`, `pattern`, `format`, `minimum`, `uniqueItems`) leaves the type as it is; `not`, `if`/`then`/`else` of any other shape and the other conditional keywords leave it wider. The validator checks all of them. Arrays and objects are mutable, as json-schema-to-typescript's were, except a `const` or `enum` value, which is typed as `as const` would type it.
- **A `/** */` comment before a key is a doc comment,** the maintainer's choice of 2026-10-26. The question was the maintainer's: "how do we incorporate the description field inside of the JSON schema into the types? Do we add that as JSDoc on generated types? Similarly, do we use the comment information inside of JSONC at all? Can JSONC support JSDoc? If not, do we take any regular inline comments and apply them as JSDoc to the property that they are above?" Offered the options, the maintainer picked "Only /** */ comments — a /** */ comment above a property becomes its JSDoc where it has no description; // stays a private note, as in TypeScript". So the comment written directly before a key (no token between them, though another comment may be; the last when there are two, as TypeScript shows the last) is the JSDoc of what the key declares, wherever a `description` is one already: a property of `properties`, an entry of the root's `$defs` or `definitions`, and, written before the file's root, the root. A `description` wins over it. A `//` comment, a `/* */` comment and `/**/` are never read, and neither is a `/** */` comment anywhere else (between a key and its value, before a comma). Its text is read as TypeScript reads JSDoc: without the delimiters, without each line's leading `*` and the space after it, blank lines at either end dropped, and tags (`@deprecated`, `@example`) kept as written, so an editor shows `@deprecated` as a tag. The comments are read in both dialects by one small scanner over the source after it has parsed (`scanDocs` in `src/parse.ts`), which tells strings, comments and punctuation apart and follows the keys from the root, since JSON5's parser drops comments and JSON with comments is JSON5's syntax less some of its forms; each key is decoded by json5, so a bare, single-quoted or escaped JSON5 key is the key the parsed value holds. They are kept beside the parsed values, not in them, so the schema ajv compiles, the module's `schema` and its Standard JSON Schema stay as written; `mapSchemas` in `src/refs.ts` passes them on to the copies it makes. Measured on 2026-10-26 with the 7.1.0-beta language server: a hover over a property of a value `.is()` narrowed, of a `.schema.jsonc` and of a `.schema.json5` file, printed the comment's text after the type, and `@deprecated` as a tag. The alternatives: every comment above a property, `//` included, which would make a private note public; and `description` alone, which leaves a JSONC file's comments unread.
- **The rule: the type admits every value the validator accepts.** Each keyword's type is meant to admit every value its rule does, and `allOf`, `anyOf` and `oneOf` compose those types as intersection and union, so a keyword the emitter does not read only widens the type. Checked against ajv on 2026-10-20 for `nullable` (the one keyword found where it did not hold: ajv honours OpenAPI 3.0's `nullable: true` and the type said `string`; the type then added `null`, and since the same day neither reads it, [below](#the-validator)), `$async` (ajv made the validator return a promise, which `.is()` took for a pass; ignored since), `if`/`then`/`else`, `dependentRequired` and `$dynamicRef` (each widens). An `unevaluatedProperties: false` beside `allOf` was recorded here as widening too, and did not hold: `{ "type": "object", "allOf": [{ "properties": { "a": { "type": "string" } } }], "unevaluatedProperties": false }` accepted `{ "a": "x" }`, and its type, `{ [key: string]: never } & { a?: string }`, refused it (measured on 2026-10-20 with tsc); since then it closes the object only when nothing beside it can allow a key (above). The test in `tests/schema-types.test.ts` assigns every sample ajv accepts to the type, for these schemas and the conditionals below, and runs tsc. A schema without `type` did not hold either until the same day (above): `{ "properties": { "a": { "type": "string" } }, "required": ["a"] }` accepted `5`, `"x"` and `null`, typed `{ a: string; ... }`, and `"address": { "properties": ... }` accepted `{ "address": 5 }`, typed as an object (measured); the test checks those too. A `$ref` beside other keywords is intersected with them in every draft, as ajv applies them in draft-07 too (measured on 2026-10-20: `{ "$ref": ..., "required": ["y"] }` refused an object without `y` under draft-07), though draft-07's text ignores a `$ref`'s siblings. Three more shapes did not hold, measured on 2026-10-20 and closed the same day, each checked by the same test:
  - **A required key that `properties` does not list,** beside `additionalProperties` or `patternProperties`, was `unknown`, which TypeScript refuses beside a narrower index signature: `{ "type": "object", "required": ["a"], "additionalProperties": { "type": "number" } }` gave `{ a: unknown; [key: string]: number }`, error TS2411 in the mapper's virtual code, so a valid schema failed the type check of every project that imported it. Such a key now has the type of every `patternProperties` entry whose pattern matches it (each applies, so their union admits it), tested as ajv tests a pattern (a Unicode regular expression, unanchored), or of `additionalProperties` when none matches, since a key a pattern matches is not an additional property; `never` when the object is closed and no pattern matches it, as no value then passes, and `unknown` without `additionalProperties`. A pattern this runtime cannot read adds `additionalProperties`' type too.
  - **An optional property is `a?: T`, and `a?: T | undefined` under `exactOptionalPropertyTypes`.** ajv passes a property that holds `undefined` as absent (it checks `data.a !== undefined`), so the type admits `{ a: undefined }`, which the `?` already does unless the project turns that option on. The maintainer's answer of 2026-10-27, asked whether dotschema should stop writing `| undefined` on an optional property: "when exactoptionalpropertytypes is off the question mark adds the `| undefined` anyway". So the content mapper keeps each project's `exactOptionalPropertyTypes` from the compiler options TypeScript's `openProject` hands it, by the project's handle, and folds it into the project's `configIdentity`, so that turning the option on types the schemas again; the emitter writes `| undefined` under the option, and where no project's options are known (`schemaTypes` called outside the mapper), the type that holds under both. Measured on 2026-10-27 with the 7.1.0-beta language server on the packed package: a value `.validate()` returns, past its issues, hovers as `{ name: string; role?: "admin" | "member"; }`, and with the option as `{ name: string; role?: "admin" | "member" | undefined; }`; TypeScript's own error messages print an optional property with `| undefined` either way. A library's declarations are written as the library's own options read them, so one built without the option inlines `a?: T`, which a consumer with the option reads as refusing `{ a: undefined }`. Until then every optional property was `a?: T | undefined`, which a hover printed in every project; before that, `a?: T`, which under the option refused `{ a: undefined }`. JSON cannot hold `undefined`, so only a JavaScript value meets it. A required property that holds `undefined` is missing, for ajv and the type alike.
  - **An `$id` below a file's root is refused,** in the type check and the build, as a problem at that `$id`'s value (`embeddedIdProblems` in `src/refs.ts`), or at the root's reference to the file that holds it. ajv resolves a `$ref` inside such a schema against that `$id`, while the emitter resolves every pointer against the file: `{ "$defs": { "x": { "type": "string" }, "inner": { "$id": "https://example.com/inner", "$defs": { "x": { "type": "number" } }, "allOf": [{ "$ref": "#/$defs/x" }] } }, "allOf": [{ "$ref": "#/$defs/inner" }] }` validated `1` and refused `"s"`, typed `string`, in 2020-12 and in draft-07 with `definitions`; with the `$ref` beside the `$id`, ajv recursed until the stack ran out while compiling, reported as an invalid schema. The message names the fix: move that schema to a file of its own and `$ref` the file, or remove the `$id`. A plain-name `$id` (`"#name"`, draft-07's anchor) moves no base and stays, and so do the root's own `$id` and `$id` as data or as a property's name. Standard JSON Schema's conversion refused the same `$id`s already ([below](#standard-json-schema)); resolving each `$ref` against its `$id` in the emitter was the alternative.
  - **A `__proto__` key in `properties` was typed by its schema,** `__proto__: string` for `{ "__proto__": { "type": "string" } }`, while ajv never reads that key there (`allSchemaProperties` in `dist/vocabularies/code.js` leaves it out, as do `properties`, `patternProperties` and the list `additionalProperties` checks against): ajv 8.11.0 and 8.20.0 passed `{ "__proto__": 1 }`, read with `JSON.parse`, which makes the key the value's own (measured on 2026-10-26). ajv reads the value's own `__proto__` as an additional property instead: beside `"additionalProperties": false` it refused `{ "__proto__": "x" }`, beside `{ "type": "number" }` it took the key as a number, and `required: ["__proto__"]` still requires it (with `ownProperties`, the key must be the value's own). Since 2026-10-26 the emitter skips the key in `properties`, so it is typed as any key outside them, by the index signature, and as a required key that `properties` does not list when `required` names it: `__proto__: unknown`, `never` beside `"additionalProperties": false`, `number` beside `{ "type": "number" }` (`tests/schema.test.ts`). An `if` that tests the key's value tests nothing in ajv, so it no longer narrows a union. The alternative was a problem at the key, which would refuse a schema the spec allows, where ajv only checks less than it says; ajv's other leniencies are kept the same way ([the validator](#the-validator)). A `.pick()` or `.omit()` was already not offered for such an object.
- **The schema as written is a type of its own, `Json`:** the module declares `type Json = ` the schema's literal type and the default export as `Schema<{ … }, Json>`, so an error or a hover that names the module prints `Json` in place of the schema. With the literal inline it printed the schema itself, truncated (measured on 2026-10-20: `Type 'Schema<Type, { readonly $schema: "https://json-schema.org/draft/2020-12/schema"; readonly type: "object"; readonly properties: { ...; }; ... }>' is not assignable to type 'number'`). The type `Json` is not exported, since no consumer needs to name it: a library that re-exports a schema module still emits its declarations, TypeScript inlining the literal there (`tests/fixtures/declaration`, `tests/lab.test.ts`). A definition or another file's `Type` imported under that name takes another (`Json2`), as one named `Type` does.
- **Discriminated unions narrow:** a `oneOf` or `anyOf` of objects told apart by a `const` property is a union of object types with that property's literal type, and TypeScript narrows it in an `if` or a `switch`, exhaustively, also when the variants sit beside shared properties (an intersection with the union, which TypeScript distributes). The schema `lab/basic/event.schema.jsonc` is checked that way in `lab/basic/main.ts`. A union written with `if`/`then`/`else` narrows too, since the maintainer's pick of 2026-10-20: when an object schema's `if`, its own or that of each `allOf` member holding only a conditional, tests a required property with `const` or `enum` and nothing else, and that property's schema lists its values (`enum` or `const`, directly or through a `$ref` in the file), the conditionals are a union with one member per listed value, that value with the `then` of each test it passes and the `else` of each it fails. Every value the validator accepts has one of the listed values, so it is in that value's member, and the type stays as wide as the rule needs while TypeScript narrows on the property:

  ```jsonc
  { "type": "object", "properties": { "kind": { "enum": ["click", "visit"] } }, "required": ["kind"],
    "if": { "properties": { "kind": { "const": "click" } } },
    "then": { "properties": { "x": { "type": "number" } }, "required": ["x"] },
    "else": { "properties": { "url": { "type": "string" } }, "required": ["url"] } }
  ```

  is `{ kind: "click" | "visit"; ... } & (({ kind: "click" } & { x: number; ... }) | ({ kind: "visit" } & { url: string; ... }))`. One member per value, rather than each conditional typed as `(if & then) | else`, because an `else` cannot be typed without the complement of its `if`, and without it `(if & then) | unknown` is `unknown`; a chain of N conditionals in `allOf` would also be 2^N intersections for TypeScript to reduce. A property whose values are not listed (`{ "type": "string" }`), one that is not required, an `if` that tests two properties or anything beside `const` and `enum`, and a `$ref` to the values in another file are not read, and widen as before.
- **Compared with json-schema-to-typescript** on 19 schemas on 2026-10-09, by assignability both ways under tsc: the same type for 16. For the other 3, json-schema-to-typescript was wrong: it does not read `prefixItems`, so a 2020-12 tuple became `never[]` and an open one `[boolean, boolean, ...boolean[]]`, and it typed `{}`, which accepts every value, as an object.
- **A `$ref` to another schema file is that file's type,** imported from its module ([below](#references-to-other-files)); a `$ref` to a URL is not followed, and its type is `unknown`.
- **The schema itself is checked:** the type check compiles the schema with ajv and reports an invalid one (`tests/fixtures/errors`).

## References to other files

The maintainer's requirement of 2026-10-20: "We absolutely need to follow refs into other files." Built the same day, in `src/refs.ts` with the emitter and the validator.

```jsonc
// team.schema.jsonc, beside user.schema.jsonc and shared/place.schema.jsonc (lab/basic)
{ "properties": { "lead": { "$ref": "./user.schema.jsonc" }, "office": { "$ref": "./shared/place.schema.jsonc#/definitions/place" } } }
```

```ts
// Its module's types, as the mapper writes them:
import type { Type as User } from "./user.schema.jsonc";
import type { Place } from "./shared/place.schema.jsonc";
export interface Type {
  lead?: User;
  office?: Place;
  [key: string]: unknown;
}
```

- **Which file:** a reference's URI part is resolved against the file that holds it, as a relative URL, so `./user.schema.jsonc`, `user.schema.jsonc` and `../user.schema.jsonc` name files near it and a reference in another file resolves against that file. A `$id` does not move it: files are the unit, as TypeScript's imports are. A reference with a scheme of its own (`https:`, `urn:`, `file:`) is a URL and is not followed; ajv reports it, as before. The file must be a `.schema.jsonc` or `.schema.json5` file, so that its module is a schema's.
- **The type is an import of the other file's module,** so TypeScript sends that file through the mapper itself, with no `dynamicConfig` (measured with a probe mapper on 2026-10-20, Motherload's PLAN.md, "Content mapper facts"; `lab/basic/shared/place.schema.jsonc` is reached only this way, and its type is checked exactly in `lab/basic/main.ts`). A pointer to the file's root is its `Type`, imported under a name for the file (`./address.schema.jsonc` is `Address`); a pointer to an entry of its `$defs` or `definitions` is the type its module declares for it, under that name; a name taken in the importing module gets `2`, as a definition's does. A pointer to anything else is inlined from the other file, whose own references are imported in turn. An anchor there (`./user.schema.jsonc#city`) is read as a pointer to the schema that declares it. Two files that refer to each other import each other, which TypeScript allows.
- **The importing module's text depends on the other file:** the names it imports and what it inlines. TypeScript transformed every mapped file on every `--incremental` run and on every change under `--watch` (measured on `7.1.0-dev.20261002.1`, Motherload's PLAN.md, "Content mapper facts"), so the text is never stale on that build.
- **Anchors are found where ajv finds them:** an `$anchor`, a `$dynamicAnchor` or a plain-name `$id`, in every draft, in each schema ajv 8.20.0 walks for them (`getSchemaRefs` in its `dist/compile/resolve.js`, with json-schema-traverse's `allKeys`), mirrored by `anchorsIn` in `src/refs.ts`, so the types resolve exactly the anchors the validator does. That walk leaves out two places the spec does not: measured on 2026-10-26, ajv refused a `$ref` to an anchor declared at a file's root ("can't resolve reference #top from id dotschema:0", with and without an `$id`) and to one inside `prefixItems`, and resolved one under a keyword no draft defines and one under `dependentSchemas`. A `$ref` to an anchor in those two places is a problem at the reference whose message gives the pointer ajv does follow (`write "#/properties/g/prefixItems/0" in its place`); one to an anchor no schema declares is a problem too. A `$dynamicRef` is not read by the types and still widens ([above](#the-types)); a `$ref` to a `$dynamicAnchor` is read as one to a plain anchor, as ajv reads it (measured the same day).
- **The validator is compiled from every file the schema reaches,** transitively, in one ajv instance: each other file is added with `.addSchema()` and the root compiled, so a cycle between files validates. The module still imports nothing, and `schema` is the root file's own schema, its references as written.
- **No path in the module:** ajv's standalone code embeds each schema's `$id` (measured: with file URLs as ids, the module held the absolute path four times). Each file is given an id with no path, its own `$id` when that has a scheme and `dotschema:<n>` otherwise (`motherload:<n>` until the extraction), and each reference to another of the files is rewritten to that file's id, keyword by keyword (`properties`, `items`, `allOf` and the rest), so data under `const`, `enum`, `default` or `examples` that holds a `$ref` key stays as written (`tests/schema.test.ts` checks that the module holds no part of its directory's path).
- **One draft:** every file is compiled in the root's draft. A file that declares another `$schema` than the root's (drafts 06 and 07 count as one) is a problem; a file that declares none is read in the root's.
- **Problems are placed at the reference** in the root's text: a file that does not exist, cannot be read or does not parse, a file that is not a schema file, a pointer to nothing (`#/$defs/nope`), a pointer to a value that is not a schema (`#/required`, a list of names), an anchor the file does not declare, a draft that differs. A reference within its own file is checked the same way since 2026-10-26: before, ajv reported a pointer to nothing there at the file's first character, naming the file by its internal id (`can't resolve reference dotschema:1#nope`), and a pointer to a list was not reported at all, typed `unknown`, while the validator passed `["name"]` and `5` alike (measured that day on `./user.schema.jsonc#/required`). A target that is an object passes, whatever keyword holds it. A problem in a file the root reaches through another is placed at the root's reference to that file, its message prefixed with the file (`./via.schema.jsonc: The $ref ...`). The reference's type is `unknown`, so the problem is the one error. A referenced file's own problems are also reported in that file, which the import brings into the program (`tests/fixtures/errors/broken-ref.schema.jsonc` is reported at line 4, column 35).
- **Bundlers rebuild on a change to a referenced file:** the loader's `load` returns the files it read as `watchFiles`, which the esbuild plugin passes on as its `watchFiles`, the webpack loader to `addDependency` and the Vite plugin to `addWatchFile`, also when the module fails, so creating a missing file rebuilds it; the Jest transformer's cache key is the module itself, which a change to a referenced file changes (`tests/adapters.test.ts`). The esbuild bundle of `lab/basic` counts `team.schema.jsonc` as one input: the files it refers to are compiled into its validator. The Node and Bun preloads build each module once and watch nothing.
- **Nothing is shared or cached between modules,** the maintainer's question of 2026-10-20 ("if there's a bunch of imported schemas that all reference some shared schema"): each module reads, parses and compiles every file it reaches, and carries its own compiled copy of them. Measured that day with ten schemas that each refer twice to one shared schema of six properties (`pattern`, `email`, `date-time`), against one: a module built in 7 ms once ajv was loaded (40 ms for the first, which loads it), `tsc` took 377 ms against 315 ms, and the esbuild bundle was 188 KB minified (6.3 KB gzipped) against 18.8 KB (3.8 KB), growing with each schema. So caching the compile by path would save milliseconds, and was not added; the size is the cost. Of a module's bytes, a schema of `type: "string"` alone was 1.3 KB minified, and a `format` ajv-formats checks with a function (`date-time`) added 7.4 KB, because ajv's standalone code required ajv-formats' whole formats module, which was inlined whole (a regular-expression format such as `email` added 0.3 KB); since 2026-10-26 a module inlines only the files of the formats it uses ([below](#formats)). Sharing would mean modules that import the modules of the files they refer to and call their validators, which ajv's standalone code cannot link ([PLAN.md](./PLAN.md#open)).

## The suffix

A schema file's suffix is `.schema.jsonc` or `.schema.json5`, and the suffix names the dialect the file is read in (the maintainer's decisions of 2026-10-20: `.schema.jsonc` in the morning, then `.schema.json5` beside it, "I think we can continue supporting it for .schema.jsonc and .schema.json5. Kind of nice to be able to have comments as well."). It was `.schema.json` until 2026-10-19, then `.jsonschema` for a day (the maintainer's answer of 2026-10-19, replaced on 2026-10-20). [microsoft/TypeScript#64581](https://github.com/microsoft/TypeScript/pull/64581), merged 2026-10-13, refuses a content mapper extension that ends in a built-in one with the TS18066 that `.json` itself gets, and the `release-7.1` branch, cut as `7.1.0-beta` on 2026-10-16, carries it. Measured on 2026-10-19 with a tsconfig registering `.schema.json`, `.sql` and `.pg.sql` for a probe mapper: `7.1.0-dev.20260929.1` accepted all three, and `7.1.0-dev.20261019.1` reported `TS18066: Content mapper file extension '.schema.json' is a built-in extension and cannot be registered by a content mapper` and accepted the other two. The pinned `7.1.0-dev.20261002.1` predates the rule.

- **What the rule reserves:** the pattern `/\.(?:[cm]?[jt]s|[jt]sx|json)$/i` (`packages/typescript/src/vscode/extensionApi.ts` in the PR, whose test lists `.ts`, `.tsx`, `.mts`, `.cts`, `.js`, `.jsx`, `.mjs`, `.cjs`, `.json` and `.d.ts` and its kin), so `.jsonc` and `.json5` are not built-in and neither schema suffix ends in one. The PR's subject is the output extensions of a mapped file that another tool emits to disk, not JSON. Measured on 2026-10-20 on the released `7.1.0-beta` (on npm since that day, installed with nub's `--minimum-release-age=0` on the maintainer's word): the four projects of Motherload's `nub run typecheck` pass, `lab/basic` registering both schema suffixes; `tests/fixtures/errors` gives the same diagnostics as on the pinned build, `broken.schema.json5(3,44)` among them; and an entry registering `.schema.json` and `.schema.json5` gets TS18066 for the first alone.
- **The suffix names the dialect:** `parseSchemaFile` in `src/schema.ts` reads a `.schema.jsonc` file as JSONC (comments and trailing commas), with the parser of the `.jsonc` loader, and a `.schema.json5` file as JSON5 (also unquoted keys, single quotes, hex numbers, `Infinity`), with the parser of the `.json5` loader, each placing its syntax errors. The same text under the other suffix is a syntax error, so a file reads one way wherever it is opened (`tests/schema.test.ts`; `tests/fixtures/errors/broken.schema.json5` is reported at its line and column). Both give the same module.
- **A byte order mark at the start is read past, in both dialects,** since 2026-10-26, at the coordinator's request, after it was measured with a project whose `.schema.jsonc` and `.schema.json5` were saved with one (`EF BB BF`): the type check's host strips it, so `tsc --runExternalCode` passed and the transforms' `content` began at `{` (`TS_CONTENT_MAPPER_DEBUG=1`), while the preload and the esbuild plugin hand over the file as Node reads it, mark and all, and jsonc-parser 3.1.0 and later refuse it, so the same project failed under the preload and in the bundle with `dotschema: …/a.schema.jsonc: Invalid Symbol`; json5 read past it already. Now `parseSchemaFile` (`src/parse.ts`) reads past a leading U+FEFF in both dialects, so the hosts agree, and adds one to a problem's place, which stays the text's own. Only the start: a U+FEFF anywhere else is a syntax error in a `.schema.jsonc` file, as JSON's white space is ([Packaging](#packaging)). A test in `tests/schema.test.ts` runs both files under the preload and in an esbuild bundle and places a syntax error after the mark; it failed without the change.
- **The docs show `.schema.jsonc`, and `.schema.json5` in one line** (the maintainer, later on 2026-10-20: "the docs should only document .schema.jsonc", then "You should document that json5 is supported, but do it in a one-liner in a callout or something."): Motherload's README and docs page documented `.schema.jsonc`, and their setup's extension list ended at it, with a note at the end of each one's `.schema.jsonc` section that a schema can be a `.schema.json5` file, which a project adds to its `extensions` list itself. Here the README was the only documentation until 2026-10-27 (the maintainer, 2026-10-21: "The new package doesn't need a documentation site. It can just have a README."), and it does the same, with the note as a `[!NOTE]`; the docs site does too, with the note as a callout ([below](#the-docs-site)). The `lab/basic` project and the tests keep covering `.schema.json5`.
- **Editors:** VS Code's `jsonc` language lists `.jsonc` (`extensions/json/package.json` in microsoft/vscode), and its JSON language service runs on `json` and `jsonc` documents (`extensions/json-language-features/client/src/languageParticipants.ts`); a file names its own schema with `$schema` (VS Code's `docs/languages/json.md`), so a `.schema.jsonc` file whose `$schema` names a draft is checked and completed against that draft. VS Code's built-in mapping of `*.schema.json` to draft-07 (`jsonValidation` in `extensions/json-language-features/package.json`) does not reach `.schema.jsonc`. VS Code lists no JSON5 language, so a `.schema.json5` file gets highlighting from an extension and no schema checking. On GitHub, Linguist (`lib/linguist/languages.yml`) lists `.jsonc` under JSON with Comments and `.json5` under JSON5, so both are highlighted.
- **The alternatives:** `.jsonschema`, one word and the format's name, which no VS Code language and no Linguist language lists, so it is plain text on GitHub and in an editor without `"files.associations"`, and VS Code's JSON service never runs on it; the one thing it would guard against, TypeScript later reserving `.jsonc` or `.json5`, no rule does today, and such a rule would also take the `.jsonc` and `.json5` data loaders. Also: asking the TypeScript team to exempt `.schema.json`, which is unlikely, since the rule extends the ban on built-in extensions rather than standing apart from it, and keeping `.schema.json` until the next TypeScript bump, which it would not survive.
- **TypeScript's own type for a `.schema.json` import cannot carry a schema module,** measured on 2026-10-21 on `7.1.0-dev.20261002.1` with `resolveJsonModule`, the maintainer asking whether dotschema could be made compatible with it. The default import is the file's whole value with every literal widened: `"type": "object"` is `string`, an `enum` and `required` are `string[]`, a `const` is `string`, so no type, nor any type-level function of it, still says which keys are required or which values are allowed. Under `module: nodenext` an ES module must add `with { type: "json" }` (TS1543), every named import is refused (TS1544) and a namespace import holds `default` alone; under `preserve`, `esnext` with `bundler` resolution and `commonjs`, each top-level key is a named import too (`properties`, `"x-validate"` by its string name) and the namespace is the object. A top-level `default` keyword leaves the default import the whole object. Nothing in it is a type (`import { type Type }` is TS2305), it cannot be added to (a module augmentation of the file is TS2671, "resolves to a non-module entity"), and `user.validate()` is TS2551. Key names are not the obstacle: a default export that was the schema object itself, with `validate`, `is` and `~standard` added, would meet the type, since no draft defines a keyword of those names, and a schema would collide only through a top-level keyword of its own by one of them.
- **Around TypeScript's type, both measured the same day:** a declaration file beside the schema, `user.schema.d.json.ts`, with `allowArbitraryExtensions` (TS6263 without it), is what TypeScript resolves the import to in place of the JSON, so under `preserve` and under `esnext` with `bundler` resolution `.is()` narrows and `import { type Type }` works; under `nodenext` TypeScript holds it to its rules for JSON in an ES module (the attribute, TS1544 for `import { type Type }`, and the default import typed as the declaration file's namespace, so `user.is` is TS2339); and it is a file generated on disk for every schema, kept in step by a watcher, the step a content mapper removes. A `declare module "*.schema.json"` takes the import on this build even with `resolveJsonModule` and the file in the program, and gives every schema one type. Node 26.11.1 is not the obstacle: a `registerHooks` load hook that returns a JavaScript module for a `.schema.json` URL is used with `with { type: "json" }` and without it.
- **Not by content:** a `.jsonc` or `.json5` file is a schema by its suffix alone, the maintainer's answer of 2026-10-21 ("By the suffix alone, as now") to whether a file with a `$schema`, or one whose `$schema` names a json-schema.org draft, should become a schema module. In a data file `$schema` names the schema the file follows: measured that day over the 43 `.jsonc` and `.json5` files outside `node_modules` in the maintainer's projects, 17 had a `$schema`; the 9 that named a draft were Motherload's own `.schema.jsonc` files (now this repository's), and the other 8 were configs naming the schema they follow (five `biome.jsonc`, a `wrangler.jsonc` with `"$schema": "node_modules/wrangler/config-schema.json"`, an `opencode.jsonc`, a `config.jsonc`), each of which would have become a validator. Reading a draft `$schema` alone would leave a schema without `$schema` as data, make an import's type turn on one string inside the file, and make Motherload's `.jsonc` and `.json5` loaders either depend on ajv or read such a file otherwise than dotschema does.
- **Beside `.jsonc` and `.json5`:** the longest suffix wins in TypeScript, so with Motherload's entry for `.jsonc` and `.json5` beside dotschema's for the two schema suffixes, a schema reaches dotschema and any other `.jsonc` or `.json5` file Motherload. In a runtime or a bundler the loaders agree the same way through the protocol they share ([below](#the-shared-protocol)): `tests/interop.test.ts` checks it against a stand-in for Motherload's `.jsonc` loader, and `tests/motherload.test.ts` against a Motherload checkout. Inside Motherload, until the extraction, one loader routed every path by its longest suffix (`tests/formats.test.ts` there), and `lab/basic` registered all four suffixes in one tsconfig entry.
- **Without dotschema's loader, a runtime reads a schema as data or refuses it.** Measured on 2026-10-20 with `import user from "./user.schema.jsonc"` in `lab/basic`: Node with no loader stops with `ERR_UNKNOWN_FILE_EXTENSION`; nub 0.9.6 and Bun 1.4.3 with no loader load the file as JSONC data, so the default export is the schema object, with no validator on it, though the type check says it is a validator. Measured later that day with `import point from "./point.schema.json5"`: Node 26.11.1 and nub 0.9.6 stop with `ERR_UNKNOWN_FILE_EXTENSION`, and nub did the same in that run for `./user.schema.jsonc` and `./data.json5`, inside the repository and outside it, which `NODE_COMPAT=1` in that environment explains: measured on 2026-10-25, nub 0.9.6 with no loader reads both schema files as data with the variable unset and stops with `ERR_UNKNOWN_FILE_EXTENSION` with it set ([below](#nub-and-bun)); Bun 1.4.3 loads the file as JSON5 data, with no validator on it. With `motherload/register` (Node and nub through `--import`, Bun through `--preload`) every runtime gave the validator module for both suffixes; measured again on 2026-10-21 with `dotschema/register` on Node 26.11.1 (`node --import`), nub 0.9.6 (`nub --import`) and Bun 1.4.3 (`bun --preload`). A project that imports a schema must register dotschema's loader in every runtime it runs under.
- **Vite:** on Vite's main branch, read on 2026-10-20 and not run, the JSON transform is rolldown's native `builtin:vite-json` (`crates/rolldown_plugin_vite_json` in rolldown/rolldown), which takes only ids that end in `.json` or `.json?`, so neither schema suffix meets it. The pattern `\.(?:json|json5)(?:$|\?)` is still Vite's `isJSONRequest` (`packages/vite/src/node/plugins/json.ts`): in a module runner's SSR transform with `json.stringify: true` and `namedExports` off (`server/transformRequest.ts`), it sends a matching id's code through `ssrTransformJSON`, which replaces the first `export default` with an assignment in place of transforming the module. That reaches a `.schema.json5` file as it does a `.json5` one, and not a `.schema.jsonc` file. Measured on 2026-10-25 with Vite 8.3.4 and dotschema's plugin, the module still works there ([below](#the-vite-plugin)).

## The validator

```ts
import user, { type Type as User } from "./user.schema.jsonc";
user.validate(input);           // { value: input }, or { issues } with every issue; never throws
user.is(input);                 // input is User, stopping at the first failure
user["~standard"].validate(x);  // Standard Schema v1: the same function as validate
user["~standard"].jsonSchema;   // Standard JSON Schema v1, below
user.schema;                    // the JSON Schema, typed as a literal
```

- **The `.validate()` and `.is()` methods, and nothing that throws,** the maintainer's decision of 2026-10-20: "We should not provide any method that throws an error. Does AJV not let you produce a complete array of issues, or does it? In my opinion, there should be a `validate` method that returns complete error information, and then the `is` method can return at the first failure and give you back a boolean and/or act as a type guard. Why don't you write all this up as a TypeScript interface?" The interface was written, and the answer was "Build it as written". The `.validate(value)` method returns Standard Schema's result with dotschema's issues, `SchemaResult<T>`: `{ value }`, the value it was given, the same object, or `{ issues }`, every issue, typed as a tuple of at least one, and no `value`, as Standard Schema's `FailureResult` has none, so `value` is read once `issues` is checked (the maintainer's choice of 2026-10-27, "Match Standard Schema", asked whether an unguarded `.value` should be a type error as in Standard Schema; until then the failure declared `value?: undefined`, carried from Motherload, which made `result.value` read without that check `T | undefined` where Standard Schema's type refuses it, TS2339, measured with tsc that day); `~standard.validate` is the same function (`user.validate === user["~standard"].validate`), so a Standard Schema library gets the same issues. The `.is(value)` method is a type guard. The `schema` property is the schema as written, its `$ref`s to other files and the keywords dotschema ignores (`nullable`, `$async`) included, so a tool that wants the schema to `~standard.jsonSchema.input({ target })`, which is self-contained and leaves those keywords out. Nothing on the module throws but `~standard.jsonSchema` for a target it cannot produce, which Standard JSON Schema requires ([below](#standard-json-schema)); where ajv itself throws, both methods answer instead (below). The package exports `SchemaResult` and `SchemaIssue` beside `Schema`. In the type, `~standard`'s own `.validate()` comes first in the intersection with Standard Schema's props, so that `user["~standard"].validate(x)` is typed `SchemaResult<T>`: with Standard Schema's first, the call took its signature, a result or a promise of one (measured with tsc on 2026-10-20). The alternatives: `.parse()`, the module's method until that day, which returned the value or threw a `TypeError` carrying the issues (a `SchemaError` in the types), and which the maintainer's rule takes out because it throws; and one validator for both methods, with `allErrors`, which is smaller, but `.is()` would go on checking a value it already knows fails, where the maintainer asked that it "return at the first failure".
- **Two validators in one module:** ajv sets `allErrors` per instance, so the module is built with two, one with `allErrors` for `.validate()` and one without for `.is()`, each compiled from the same files with the same formats, meta-schemas and ignored keywords (`loadAjv` and `compile` in `src/schema.ts`, run once for each). Their standalone codes are inlined into one module that shares one table of run-time modules, so a helper both require (ajv's `ucs2length`, fast-deep-equal, a format's file) is in it once (`tests/schema.test.ts`). The `.is()` method uses the second: on an object whose first property fails, it returns without reading the next one, which `.validate()` reads (a getter that counts, in the test). What the second costs, measured on 2026-10-20: `lab/basic/user.schema.jsonc`'s module grew from 8,544 to 14,573 bytes (2,601 to 3,402 gzipped), and `lab/basic/event.schema.jsonc`'s, which carried ajv-formats' formats, from 21,916 to 29,985 (5,582 to 6,518 gzipped). - **An issue** (`SchemaIssue`) is `{ message, path, keyword }`: ajv's `message`, the `path` in the value and the `keyword` that failed. The maintainer's answer of 2026-10-20 on ajv's `params` and `schemaPath`, which it carried until then: "Drop both". ajv's `schemaPath` pointed at the wrong place across `$ref`s and files: it is relative to the compiled function that raised the error, so an error in a recursive `$defs/node` read `#/properties/name/type`, which is not at the root, and one in another file read as an internal id (`motherload:1/properties/name/type`, `dotschema:1/...` since the extraction) or as the root's own (measured in the review of the interface). The path holds object keys as strings and array indexes as numbers. ajv's `instancePath` is a JSON Pointer, which writes an index as it writes a key (`/0` either way), so each unescaped segment is read against the value it names: under an array a number, under anything else a string, so `{ "map": { "0": 1 } }` gives `["map", "0"]` and `{ "list": [1] }` gives `["list", 0]`. With a precision `p`, ajv takes `x` as a multiple when `x / m` is within `10^-p` of an integer, a fixed tolerance, while a double's error in the quotient grows with it, about `q × 3e-16`: so a larger `p` refuses true multiples sooner as the quotient grows, and a smaller one lets more values just off a multiple through. Measured on 2026-10-20 over 2.7 million written multiples per range (nine steps from `0.01` to `2.5e-5`, each value as JSON writes it): `p = 9` refused none below a quotient of 10^6 and 3% between 10^6 and 10^7 (`863807.2` for `0.1`); `8` none below 10^7 (`932179.19` for `0.01` refused above it); `7` none below 10^8; `6` none below 10^9. ## Formats

The `format` keyword is checked by dotschema's own formats, in `src/formats/`, since 2026-10-26; until then by ajv-formats 3.0.1's table, registered with dotschema's ajv ([the validator](#the-validator)). The maintainer's decision of that day, asked "Which format work should dotschema build now?", ticked three options; the first is "Fix the standard formats the test suite catches: date-time, time, duration and uuid as dotschema's own copies; the rest of ajv-formats unchanged", the second "Add Zod's formats: jwt, credit_card and iban with Zod's own checks, plus Zod's regex formats for schemas written by hand", and the third "Add the IDN and IRI formats: idn-email, idn-hostname, iri, iri-reference" ([PLAN.md](./PLAN.md#decisions)). The same day the coordinator read the first as the maintainer's words, "Fix the standard formats the test suite catches", the rest of it being the option's text, so the formats kept from ajv-formats that the suite catches are dotschema's own too, and every format test of the suite passes.

```jsonc
{ "type": "string", "format": "date-time" } // checked by src/formats/date-time.cjs, inlined into the module with date.cjs and time.cjs
```

- **One table of formats,** `FORMATS` in `src/formats/index.ts`, which `loadAjv` registers with every ajv it makes, the two the build compiles a module with and the type check's, so a schema that uses a format compiles and validates in both. A format is a regular expression, which ajv writes into each validator as a literal; `true`, a known format that checks nothing (OpenAPI's `password` and `binary`), so that `formatMinimum` beside it is ignored as ajv-formats ignores it; or a file of the same directory. A name the table does not have is not checked, as before: ajv runs with `strict: false` ([the validator](#the-validator)).
- **A format checked by a function is a file of its own,** plain JavaScript in CommonJS, whose `module.exports` is the format as ajv's `addFormat` takes it: a function of the string, `{ validate, compare }` for a format with an order (`date`, `time`, `date-time`, `iso-time`, `iso-date-time`), or `{ type: "number", validate }` for a format of numbers (`int32`, `int64`, `float`, `double`). JavaScript and not TypeScript, because the repository's package points at its sources and the inliner pastes a file's text, as it pasted ajv-formats' `dist/formats.js`; CommonJS, because that is what the inliner wraps. A file uses no Node API and no `new Function` or `eval` (the module runs in browsers and in workerd, [Cloudflare Workers](#cloudflare-workers)), and requires only other files of the directory (`date-time.cjs` requires `date.cjs` and `time.cjs`). The build copies them into `dist/dotschema/src/formats/` and loads each from there (`scripts/build.ts`).
- **A module carries the files of the formats it uses, and no others.** ajv writes a function format into standalone code through its `code.formats` option, as `const formats0 = <code.formats>["date-time"];`; `loadAjv` sets it to a free name, `__formats`, and `schemaCode` reads those declarations in each validator's code (`usedFormats`), inlines each format's file, with the files it requires, into the module's table of modules, and defines `const __formats = { "date-time": __require(1) }` before the validators. Nothing in ajv's code is rewritten, so a string in the schema that holds the same text can only add a file. A module that uses no function format has no `__formats` at all (`tests/formats.test.ts`). The alternative was the whole table inlined into every such module, as with ajv-formats, whose `dist/formats.js` was 14.6 KB of source.
- **A long regular expression is a file too:** ajv writes a regular-expression format into each validator that uses it, and a module has two validators ([the validator](#the-validator)), and one more for each definition and, for `.pick()`, each property, so an expression over 400 characters (`ipv6`, `url`, `currency_code`) is a file whose function tests it, carried once. ## Standard JSON Schema

The schema module implements Standard JSON Schema v1 (`@standard-schema/spec` 1.1.0, 2025-12-15) for the `"draft-07"` and `"draft-2020-12"` targets, the two the spec "strongly recommends" (the maintainer's answer of 2026-10-20: "Yes, draft-07 and 2020-12"). A library that needs a schema as JSON Schema (an API or tool definition) reads it from `~standard.jsonSchema`:

```ts
user["~standard"].jsonSchema.input({ target: "draft-2020-12" }); // { $schema: "https://json-schema.org/draft/2020-12/schema", ... }
user["~standard"].jsonSchema.output({ target: "draft-07" });     // the same schema as input: nothing transforms the value
user["~standard"].jsonSchema.input({ target: "openapi-3.0" });   // throws, as the spec asks of a target the library does not support
```

- **Computed when the module is built** (`src/json-schema.ts`, called from `schemaCode`): the module carries each target's schema, or the reason it has none, and returns a fresh copy (`structuredClone`) on each call, so a caller may change it. The `.input()` and `.output()` methods return the same schema, since validation never changes the value.
- **Self-contained:** every other file the schema reaches through a `$ref` is folded in under the target's container (`$defs` in 2020-12, `definitions` in draft-07), keyed by its name without the suffix (`user`, `user2` when taken), and every `$ref` becomes a JSON Pointer into the one document: `lab/basic/team.schema.jsonc`'s `lead` is `#/$defs/user` in 2020-12 and `#/definitions/user` in draft-07. A folded file loses its `$schema` and `$id`; a reference to a file's absolute `$id` becomes a pointer too; a URL `$ref` is left as written. This is not 2020-12's bundling (core 9.3.1), which keeps each file's `$id` and its references as written: the verdicts are the same, and the schema paths of errors differ.
- **Converted where the two drafts say the same thing:** `definitions` and `$defs`; a list of `items` with `additionalItems` and `prefixItems` with `items`; `dependencies` and `dependentRequired`/`dependentSchemas` (a property in both is `{ allOf: [{ required }, schema] }` in draft-07); a draft-07 `$id: "#name"` and `$anchor`, every reference to an anchor becoming a pointer. Draft-07 ignores the keywords beside a `$ref` (core 8.3) while ajv and the later drafts apply them, so going to draft-07 a `$ref` with validating keywords beside it moves into `allOf`. A keyword the schema's own draft does not define (`prefixItems` in a draft-07 schema, which ajv ignored) is left out of both targets, so the target does not start applying it; a vendor keyword (`x-foo`) is kept.
- **Refused rather than approximated:** where a keyword has no exact equivalent in the target, that target throws with the keyword and its place (`./file#/pointer`), and the other target still converts. To draft-07: `unevaluatedProperties`, `unevaluatedItems`, `minContains`/`maxContains` beside `contains`, `$dynamicRef`/`$dynamicAnchor`, `$recursiveRef`/`$recursiveAnchor`. From 2019-09 to 2020-12: `$recursiveRef`/`$recursiveAnchor`, and `unevaluatedItems` in a schema that uses `contains`, which 2020-12 counts as evaluating items and 2019-09 does not (2020-12 core 11.2). In 2020-12, `$dynamicRef`/`$dynamicAnchor` across several files, whose resolution one document does not keep apart. In both: an `$id` inside a file (which the module refuses before the conversion, [types](#the-types)), a root `$id` with a fragment, a `$ref` to something that is not a schema the conversion places, and one name in both `definitions` and `$defs`.
- **Checked by equivalence** (`tests/json-schema.test.ts`): for each produced schema, ajv compiling it for its target (`ajv` or `ajv/dist/2020`, with `allErrors`, dotschema's formats, ajv-formats until 2026-10-26, and `strictSchema`, so a keyword the target would ignore fails the compile) gives the same verdict as the module's own validator on valid and invalid values, for the fixtures in `tests/fixtures/json-schema/` (2020-12, draft-07 and 2019-09, across files, with anchors, tuples and both kinds of dependency) and for `lab/basic`'s schemas; `lab/basic` prints `team`'s two conversions under the preload and from the esbuild bundle.

## Each definition a validator

The maintainer's pick of 2026-10-26, for the fragments item ([PLAN.md](./PLAN.md#decisions)): "Each $defs entry importable as its own validator — import { address } from "./user.schema.jsonc", with address.validate() and address.is()".

```ts
import user, { address } from "./user.schema.jsonc"; // lab/basic: "definitions": { "address": { ... } }
address.validate(input); // { value } or { issues }, as user.validate
address.is(input);       // input is address.Type
address["~standard"].jsonSchema.input({ target: "draft-2020-12" }); // the definition as a document of its own
```

- **Every entry of the root's `$defs` and `definitions`** whose value is a schema (an object or a boolean) is a named export with the module's own surface: `.validate()`, `.is()`, `schema` (the entry as written), `~standard` with Standard JSON Schema, and `.pick()` and `.omit()` where it is a plain object ([below](#pick-and-omit)). Its type is `Schema<{ … }, Json["$defs"]["address"]>`, written out as the root's is, and a namespace of types merges with it as with the default export, `export declare namespace address { export type { Address as Type }; }`, so `address.Type` is the definition's type. The type check compiles each definition as the build does, so one ajv refuses is a problem in both.
- **The name is the key in camelCase:** the key split at every character that is not a letter or a digit, the first word's leading capitals lowered (`HTTPServer` is `httpServer`, `URL` is `url`, `Address` is `address`), the others capitalized (`my-address` and `my_address` are `myAddress`); `_` before a leading digit (`2fa` is `_2fa`); `_` after a word a module cannot bind or should not shadow, JavaScript's reserved words, `arguments`, `eval`, `undefined`, `NaN`, `Infinity`, `globalThis`, TypeScript's names for its own types (`string`, `number`, `object`, `any` and the rest, which a namespace may not take) and `schema`, the module's own name for its default export (`default` is `default_`); `definition` for a key with no letter or digit; and a number after a name already taken, by an earlier key or by any type the module declares, in the order the module declares them, `$defs` before `definitions` (`my-address` then `myAddress` give `myAddress` and `myAddress2`; `2fa`, whose type is `_2fa`, gives `_2fa2`). So every name is an identifier the module exports as a `const` and the Jest transformer's rewrite keeps (`valueName` in `src/schema-types.ts`, `tests/definitions.test.ts`). The alternatives were the key as written, which a key such as `my-address` or `default` cannot be as a `const`, and an export under a string name (`export { x as "my-address" }`), which an import has to rename and the CommonJS rewrite does not take.
- **Compiled on its own, so a bundler drops what nothing imports:** each definition's two validators are standalone code of their own, inside a function marked `/* @__PURE__ */`, as the default export's are, so esbuild leaves out a definition nothing imports, and the root when only a definition is imported. Measured on 2026-10-26 with esbuild 0.28.2, bundling and minifying a file that imports `lab/basic/user.schema.jsonc` (`tests/definitions.test.ts` checks which validators each bundle holds): the default export alone 13,480 bytes (3,170 gzipped), the default and `address` 15,829 (3,444), `address` alone 6,348 (2,188); with the code of 2026-10-25, which had no `address` export, the default alone was 14,435 (2,913). One standalone compile with every export in it (`standaloneCode(ajv, { … })`, which writes a function two exports share once) was measured against it and refused: for `user.schema.jsonc`'s root and `address`, 5,002 bytes minified against 5,133 for the two compiled apart with all errors, 4,935 against 5,070 without, and the bundle would carry every definition whether or not it is imported. A definition the root refers to is compiled in both when both are imported; that is the 131 bytes.
- **Its Standard JSON Schema is the definition at the document's root** (`entry` in `src/json-schema.ts`): what it reaches, transitively, is folded in under the target's container, the root file's other definitions under their keys, another file under its name as for the root, and the rest of the root file, when the definition refers to it (`{ "$ref": "#" }`), under the file's name (`#/definitions/user`); what it does not reach is left out, and so are that part's conversion errors. `tests/definitions.test.ts` compiles each document with ajv and compares the verdicts.
- **Every host loads it:** the named exports are ES module exports, so `lab/basic` imports `address` under the preload, nub and Bun and from the esbuild bundle; `lab/bundlers` under webpack, Rspack, Vite for Node and the browser, Rollup and Rolldown; `lab/jest` in Jest's CommonJS and ES module runs and Vitest (`tests/lab.test.ts`, 2026-10-26).

## Pick and omit

The maintainer's pick of 2026-10-26: "Methods in TypeScript — user.pick("id", "name") and user.omit("id"), as in Zod, each giving a new schema at run time", offered with the note that "validators are compiled at build time, so a subset chosen at run time needs every property's validator compiled separately and joined at run time, or ajv shipped at run time, which dotschema avoids today". JSON Schema has no keyword for it ([PLAN.md](./PLAN.md#decisions)).

```ts
const summary = user.pick("name", "role");   // the schema whose properties and required keep name and role
user.omit("email");                          // the schema without email
type Summary = StandardSchemaV1.InferOutput<typeof summary>; // { name: string; role: "admin" | "member" }
summary["~standard"].jsonSchema.input({ target: "draft-07" }); // that filtered schema, exactly
```

- **The schema it gives** is the JSON Schema whose `properties` and `required` keep the keys named (`.omit()`: the others), every other keyword as it was, so with `additionalProperties: false` a property left out is an additional one, and with a schema in `additionalProperties` it is checked against that. Its `schema` and Standard JSON Schema are that schema, its validators that schema's, and it has `.pick()` and `.omit()` again, so calls chain. A key the schema does not name, and any argument at all, never throws.
- **Where:** a root or a definition that is a plain object, `type: "object"` with nothing beside `properties`, `required` and `additionalProperties` (a boolean or a schema) that ajv acts on, so annotations, `$defs`, `$schema`, `$id` and a keyword ajv does not know may be there (`objectShape` in `src/schema.ts`). And filtering must give that schema: no `$ref` in its own self-contained document (above) points to it or into its `properties`, since the filtered schema's `#` is the filtered schema while each property's validator was compiled against the whole one (a tree whose children `$ref` `#`), and no file uses `$dynamicRef` or `$recursiveRef`, whose scope may reach it. Elsewhere the methods are not on the value, and not in its type, so a call is a type error (`event.pick` in `lab/basic/main.ts`). The alternatives: `patternProperties`, `minProperties` and `maxProperties` beside the properties, which filtering keeps and the join could check, left out of the first cut; and every object schema, whose `allOf`, `oneOf` or `if` would hold properties filtering does not reach.
- **One validator per property, joined at run time:** ajv compiles each property's schema on its own, from its place in the root (`getSchema` of `#/properties/<key>`), so its `$ref`s resolve as in the root, and a `$ref` that only points to another schema takes the function the root's own validator compiled for it (`shareRef`), so `team.schema.jsonc`'s `lead` and the items of `members` share one function for `user.schema.jsonc`, as in the root's validator. A property whose schema ajv takes as always valid (`true`, `{}`, a schema of keywords ajv does not know) has none, as ajv checks and reads nothing for it. At run time `__join` makes ajv's object checks around them in ajv's order, read from the code ajv 8.20.0 writes: `type` (`must be object`, and nothing else for a value that is not one), each `required` key (`must have required property 'name'`), each own key outside `properties` (`must NOT have additional properties`, or that schema's issues at the key), then each property present in `properties`' order, with ajv's reads (a property is the value's own, `ownProperties`) and its JSON Pointer escapes. For `.validate()` every error, as ajv's `allErrors`; for `.is()` it stops at the first, with the property validators compiled without `allErrors`.
- **The join is the root's validator too,** for a plain object root or definition: the module no longer carries ajv's function for the root itself, so `.pick()` costs no second copy of each property's code. Measured on 2026-10-26 on `lab/basic/user.schema.jsonc` as it was before the `address` definition, with esbuild's `--minify` of ajv's standalone code for one validator: ajv's root function, as until then, 3,272 bytes; the root's function calling one function per property (each property a `$ref` to a definition of its own in the copy ajv compiles, with `inlineRefs: false` so ajv calls rather than inlines them) 4,401, or 4,603 keeping `inlineRefs` and making each definition one ajv will not inline; the property functions alone, joined at run time, 2,230, beside the join, written once per module. Whole modules, minified (gzipped), with the code of 2026-10-25 and with this: that `user.schema.jsonc` 10,121 (2,486) and 9,689 (2,733); `lab/basic`'s `user.schema.jsonc` with `address` 14,566 (2,934) and 15,951 (3,451), which adds the `address` export; `team.schema.jsonc` 22,504 (3,759) and 21,183 (4,080); `point.schema.json5` 7,398 (1,965) and 7,762 (2,246); and `event.schema.jsonc`, a `oneOf`, which carries neither the join nor the methods, 19,976 (4,412) and 20,027 (4,445). So a minified plain object's module is smaller, and gzipped it is 247 to 321 bytes larger, the join's, where gzip had already folded the root's repeated code.
- **Checked against ajv:** `tests/pick.test.ts` builds a schema of every property kind (checked, `true`, `{}`, `false`, an annotation alone, two `$ref`s to one definition, a key only `required` names, keys a JSON Pointer escapes) in 2020-12 and draft-07, with `additionalProperties` false, absent, `true` and a schema, and for each set of keys picked and omitted, and chained, compares the Standard JSON Schema with the filtered document, `.validate()`'s issues with those of ajv compiling that document with dotschema's options, in order, and `.is()` with ajv's first-failure verdict, on values that fail every check at once, inherited keys among them. The root's own verdicts are checked against ajv by `tests/json-schema.test.ts` and `tests/verdicts.test.ts`, as before.
- **The types print the properties:** `ObjectSchema<T, S, K>` in `src/index.ts` extends `Schema<T, S>` with `pick<P extends K>(...keys: P[])` and `omit`, whose results are typed by a mapped type with an `as` clause over `keyof T`, which keeps each property's `?` and the index signature that `additionalProperties` gives, so a key left out of an open object is still allowed; `K` is the keys `properties` and `required` name, so the editor completes them and another is a type error. Measured on 2026-10-26 with the 7.1.0-beta language server: `const summary = user.pick("name", "role")` hovers as `ObjectSchema<{ name: string; role: "admin" | "member"; }, unknown, "name" | "role">`, `StandardSchemaV1.InferOutput<typeof summary>` as `{ name: string; role: "admin" | "member"; }`, a value `summary.is()` narrows as the same, one `user.omit("role", "tags", "address")` narrows as `{ name: string; email?: string | undefined; }`, and the completions inside `user.pick("")` are `name`, `address`, `email`, `role` and `tags`. A picked schema's type is not given a name of its own: `StandardSchemaV1.InferOutput` names it, and its `schema` is `unknown`, the filtered schema at run time.

## Diagnostics

- **Shown as `dotschema<code>`:** the mapper answers `initialize` with `diagnosticSource: "dotschema"`. Codes: 1 a syntax error, 3 a file whose suffix dotschema does not read (a tsconfig entry listing another extension), 4 the schema, 5 an option in tsconfig; Motherload's numbers, of which 2 has no case here ([above](#the-extraction-from-motherload)).
- **Positions are UTF-8 bytes.** The mapper declares `positionEncoding: "utf-8"` and converts the parsers' UTF-16 offsets (`utf8Range`), as Motherload's does (`tests/mapper.test.ts` places an error after an `é`).
- **A range never runs past the end of the file.** TypeScript refuses a whole transform response one of whose diagnostics does: measured on 2026-10-26 on the pinned nightly and on `7.1.0-beta`, a `.schema.jsonc` or `.schema.json5` file cut off after a property, or empty, gave `TS18069: The content mapper 'dotschema' failed to transform this file. The content mapper returned an invalid transform response.` in place of its syntax error, because jsonc-parser and json5 place an error at the end of the text, and `utf8Range` made every range at least one byte long, so it ended a byte past the end. A range is now cut at the end of the text, and one at the end is empty, which TypeScript places at the last line (`tests/fixtures/errors/truncated.schema.jsonc(3,1): error dotschema1: Close Brace Expected`; `tests/lab.test.ts`, `tests/mapper.test.ts`). Motherload's `utf8Range` is the same code (its `packages/core/src/universal.ts`, read that day, not run), so its data loaders likely share the fault ([PLAN.md](./PLAN.md#open)).
- **A schema that does not parse is typed `any`,** `Type` included, so the diagnostic in the file is the one error and every use of the import stays quiet.

## The webpack loader

- **One loader for webpack, Rspack and Turbopack,** `dotschema/webpack`, and the same function as `dotschema/turbopack`, as Motherload's `motherload/webpack` and `motherload/turbopack` are, the maintainer's answer of 2026-10-21 for Motherload and Reylo alike ("Rename to Webpack in both, but let's also include /turbopack", Motherload's DESIGN.md). A rule names it for the two suffixes, `{ test: /\.schema\.(jsonc|json5)$/, use: "dotschema/webpack" }`.
- **The files a schema refers to are watched** through `this.addDependency`, also when the module fails, and a file with a query passes through as it came (`tests/adapters.test.ts`).
- **Every rule that matches a file runs, in webpack and Rspack,** so beside Motherload's `.jsonc` loader both loaders run on `user.schema.jsonc`, and Motherload's, outranked, passes it on: it finds dotschema's function, marked under `Symbol.for("motherload.plugin")`, among the loaders on the resource.
- **Rspack loads a loader only when its turn comes:** its `runLoaders` (2.2.9, `dist/index.js`) calls `loadLoader` on each loader just before running it, where webpack loads every loader on the resource before the first runs, and a loader's `normal` is `null` until then. So under Rspack the loader that runs first, the last rule's, sees no mark of the ones that run after it. Measured on 2026-10-25: with dotschema's rule before the stand-in's `.jsonc` rule, the stand-in ran first, saw `normal: null` for dotschema's loader, made a data module of `user.schema.jsonc`, and dotschema's loader failed on that JavaScript ("Invalid Symbol"); against Motherload's real loader the same order failed on `point.schema.json5` (`tests/motherload.test.ts`). webpack 5.112.0 passed in both orders.
- **So dotschema's loader reads the file from disk where a loader it outranks is on the file:** a sibling that claims the file less strongly is a sign that what dotschema is handed may be that loader's module. Under webpack that sibling passed the file through, so the two texts are the same. Both orders now pass in Rspack, against the stand-in and against Motherload (`tests/interop.test.ts`, `tests/motherload.test.ts`), and fail without the change. The alternatives: a weaker loader that resolves a sibling not yet loaded by its path, to see its mark, which is a change to Motherload's adapter, the weaker side, and was not made here; and a rule order a project must keep under Rspack, which webpack does not need. Motherload's own Rspack test (its `tests/packages.test.ts`) passes in both orders because its stand-in for dotschema ignores what it is handed, so it does not see this.
- **Bundles:** webpack 5.112.0 and Rspack 2.2.9 bundle `lab/bundlers/main.js` into files that print what `lab/basic` prints under the preload, with no error or warning and no module from `node_modules`, and run alone in an empty directory (`tests/lab.test.ts`).

The actions are pinned at Motherload's commits (`actions/checkout` v7.0.1, `nubjs/setup-nub` v0.6.0 with nub 0.9.6). The workflow `.github/workflows/test.yml` installs the host labs and Bun 1.4.3 and runs the same four checks on every push to `main` and every pull request against it, where `tests/motherload.test.ts` is skipped, since `MOTHERLOAD_DIR` is unset.
- **What differs for one package:** there is no staging order to keep (Motherload stages `@motherload/core` first and `motherload` last), so the `stage` job resolves one name in place of a list and checks the registry once; the step summary's `stager reject` and `stager await` name `dotschema@<version>`; the release notes link the docs site, as Motherload's link its own (the README on GitHub until 2026-10-27, [the docs site](#the-docs-site)). The script `scripts/bump.ts` (`nub run bump <version>`) writes the version into the one `package.json`, where Motherload's writes every manifest and the dependencies between them.
- **The environments,** created on 2026-10-21 with `gh api -X PUT repos/colinhacks/dotschema/environments/<name>` and a deployment-branch policy for `main`, match colinhacks/motherload's as read the same day, field by field: `npm` and `release-approval` each have the maintainer (`colinhacks`) as required reviewer, `prevent_self_review` off, no wait timer, custom branch policies with the one branch `main`, and administrators allowed to bypass. The repository's Actions settings are Motherload's too: every action allowed, and the token read-only by default, so each job asks for what it needs (`id-token: write` to stage, `contents: write` to release). Neither repository has a secret or a variable.
- **The manifest** names `repository` (`git+https://github.com/colinhacks/dotschema.git`), `homepage` (the docs site since 2026-10-27, and the README on GitHub before), `bugs` (the issues) and `author`; Motherload's manifests carry `repository` and `author` and neither of the others. The build copies them into `dist/dotschema` and refuses a `repository.url` other than this repository's, because the registry checks a provenance-staged version's `repository` against its provenance, and `stager` places a staged version in its release by that field (the comment on `stagedRepo` in `~/Documents/stager/stager.mjs`).

Not released yet.", with no `repository` (`https://registry.npmjs.org/dotschema`, read on 2026-10-21). A trusted publisher can be configured only for a package that exists (`npm help trust`, "Package must exist", as Motherload's DESIGN.md quotes it), and this one does, so `scripts/npm-first-publish.sh` publishes nothing: it stops if the package is missing, signs in to npm through the browser for the run alone (the login in a private file named by `NPM_CONFIG_USERCONFIG`, logged out and deleted on exit, as Motherload's script does), and runs `npm trust github dotschema --file release.yml --repo colinhacks/dotschema --env npm --allow-stage-publish`, checked with `npm trust list`; a trust already in place is checked, not created. The maintainer runs it with `bash scripts/npm-first-publish.sh`.
