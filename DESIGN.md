# dotschema: design record

Each section is one decision: what was decided, the alternatives weighed, and the evidence. Most were taken in Motherload (`~/Documents/motherload`), whose schema loader dotschema is, extracted on 2026-10-21 ([below](#the-extraction-from-motherload)); their dates and the maintainer's words are kept as Motherload's DESIGN.md recorded them at commit d21b5ac, and a path names this repository's file unless it says Motherload's. "Measured" means a command was run and its output read, in Motherload's repository or in a scratch directory before the extraction, and in this one after; measurements were taken on macOS with Node v26.10.0 and nub v0.9.5 in Motherload, and with Node v26.11.1 and nub v0.9.6 here.

## The extraction from Motherload

The maintainer's decision of 2026-10-21: "I'm trying to decide whether to extract the JSON schema into its own package, something like `dotschema`. I think it's cleaner to extract it personally. It's not really the same as the data loading that we do in the other stuff. Let's go ahead and do it. Put it into a new dir in Documents." Then: "The new package doesn't need a documentation site. It can just have a README." And: "We could always add support into Motherload later and give Motherload a dependency on dotschema, but not right now." Earlier the same day, asked whether to take schemas out of `motherload` before its first release, the maintainer had answered "Keep it in `motherload`"; Motherload's DESIGN.md (Packaging) records that answer and what was measured for it: the schema package was 1,828 of the 2,708 lines of package source and its four test files 1,626 of the 2,306 lines of tests, and ajv and ajv-formats were about 1.09 MB of `motherload`'s install.

- **One package, `dotschema`, at the repository's root,** as `motherload` is Motherload's root package: the content mapper (`typescript.contentMapper` in `package.json`), the preload (`dotschema/register`), the esbuild plugin (`dotschema/esbuild`) and the types (`dotschema`). The extensions are Motherload's, `.schema.jsonc` and `.schema.json5`. npm held a 0.0.0 placeholder of `dotschema`, the maintainer's (Motherload's PLAN.md, "Names"), so the first version is 0.0.1.
- **Taken from Motherload's commit d21b5ac,** not from its working tree: `packages/schema/src/` (the module, the emitter, the references, the Standard JSON Schema conversion, the loader and its entry points, the types), the schema tests (`tests/schema.test.ts`, `tests/schema-types.test.ts`, `tests/json-schema.test.ts`, `tests/verdicts.test.ts`, and the schema parts of `tests/lab.test.ts`, `tests/packages.test.ts`, `tests/adapters.test.ts` and `tests/mapper.test.ts`), the fixtures (`tests/fixtures/json-schema/`, `tests/fixtures/declaration/`, the schema files of `tests/fixtures/errors/`), `lab/basic`'s schema files, and the build and its check (`scripts/build.ts`, `scripts/check-dist.ts`).
- **Self-contained: the pieces of `@motherload/core` the schema code uses are copied into `src/core/`,** and the two parsers it reads a schema with into `src/parse.ts`, so the package depends on ajv, ajv-formats, jsonc-parser and json5 alone. A dependency on `@motherload/core` was the alternative: it reports every diagnostic as `motherload` (`DIAGNOSTIC_SOURCE` in its `universal.ts`), its messages name Motherload, and the Motherload packages move together at one version (Motherload's DESIGN.md, Packaging), so each Motherload release would be a dotschema dependency to move. The copy is small and changes rarely: of core's files, `src/core/universal.ts` (the loader contract and the hosts' adapters, with dotschema's diagnostic source and option message) and `src/core/rpc.ts` (the JSON-RPC server, unchanged) are whole; `src/core/serialize.ts` keeps `Value`, `propertyName`, `toJs` and `literal`, without the check that a value is one a module can carry (`assertValue`, `UnsupportedValue`), since a JSONC or JSON5 file holds nothing else (measured: json5 2.2.3 defines a `__proto__` key as an own property, and jsonc-parser's tree is read into plain objects); `src/core/problems.ts` keeps `Problem`, `Parsed`, `CODES`, `offsetOf` and `fail`, without `carry` and `BOM`; and `src/core/standalone.ts` is `combine` and `standalone` from `module.ts` for one loader, without `moduleLoader`, `valueModule` and the data module's types. Motherload's `parseJsoncFile` and `parseJson5File` are copied without `carry`, and `parseSchemaFile` moved beside them from `refs.ts`.
- **Every name a user sees is dotschema's:** the diagnostic source (`dotschema4`, not `motherload4`), the Standard Schema `vendor`, the package the generated types import `Schema` from, the loader's and the esbuild plugin's name (which a load error starts with), the message for an extension the package does not read ("dotschema reads .schema.jsonc and .schema.json5 files; …"), the option message, the message for a missing ajv ("a dependency of dotschema … reinstall dotschema"), the `$id` and Standard JSON Schema messages, the id each file gets inside ajv (`dotschema:<n>`), and the import's local name in the generated types (`__DotschemaSchema`). The diagnostic codes keep Motherload's numbers, so `dotschema4` is a schema problem as `motherload4` was; 2, a value no module can carry, has no case here.
- **The schema loader takes no `typesFrom`:** in Motherload `schemaLoader(typesFrom)` let `motherload` and `@motherload/schema` each name itself as the package the types import from; here the types always import from `dotschema`.
- **Motherload's protocol for loaders in one host is kept as it is,** global keys included, so that Motherload's `.jsonc` and `.json5` loaders and dotschema defer to each other by the longer suffix ([below](#the-shared-protocol)).
- **Not carried over:** the docs site (the maintainer: "It can just have a README"), the release workflow and its scripts at first (`.github/`, `scripts/bump.ts`, `scripts/npm-first-publish.sh`), which needed the GitHub repository; they followed it the same day, adapted to one package ([below](#releasing)), and `lab/packages`, a schema package beside a `.jsonc` package, whose place the interop tests take (`tests/interop.test.ts`, `tests/motherload.test.ts`).

## The shared protocol

A runtime or a bundler does not route by the longest suffix as TypeScript does: Node runs the hook registered last first, and esbuild runs plugins in their order, so Motherload's `.jsonc` loader would read `user.schema.jsonc` as data, its validator gone, for one order of the flags (Motherload's DESIGN.md, Packaging, "The longest suffix, in every host"). Motherload solved it among its own packages with a protocol in `@motherload/core`'s `universal.ts`, and dotschema speaks the same one (`src/core/universal.ts`), so a project can use Motherload for its data and dotschema for its schemas in any order.

- **A loader** is an object `{ name, extensions, filter, load, types }`: `extensions` the suffixes it reads, `filter` a RegExp of every path it takes, and `load(source, path)` the module's JavaScript, `{ code, problems, watchFiles? }`.
- **A claim** is the length of the longest of a loader's extensions that ends the path, 1 for a path its filter takes by name alone, 0 for one it does not take (`claim`); a loader is outranked on a path when another claims it more strongly (`outranked`), and the strongest, the first on a tie, owns it (`ownerOf`).
- **Node and Bun:** each preload adds its loader to the set at `globalThis[Symbol.for("motherload.registered")]` before it registers its hook, so the set holds every Motherload and dotschema loader in the process. A Node hook passes a file another loader in the set outranks it on to the next hook; a Bun plugin, which may not return nothing (oven-sh/bun#5303), loads it with the loader that owns it.
- **esbuild:** each plugin object carries its loader under `Symbol.for("motherload.plugin")`; a plugin finds its siblings in `build.initialOptions.plugins` and returns nothing for a file a sibling outranks it on.
- **The keys stay Motherload's,** `motherload.registered` and `motherload.plugin`: Motherload 0.0.1, published on 2026-10-21 (Motherload's commit 61c1c55), uses them, and a dotschema of its own keys would not see its loaders, nor they dotschema's. Measured with dotschema's keys changed to `dotschema.registered` and `dotschema.plugin`: `tests/interop.test.ts` failed in Node, Bun and esbuild. Either package changing the keys, the loader's shape or the rule breaks the other, so a change is made in both.
- **A tie defers to neither:** two loaders that claim one suffix, such as Motherload 0.0.1 (which reads `.schema.jsonc` itself) beside dotschema, are left to the host's order. Measured on 2026-10-21 against the Motherload checkout at its `main` (61c1c55), with `motherload` for `.jsonc` and `.json5` and dotschema for the schema suffixes: the type check passed through both mappers, since TypeScript gives the schema files to the entry with the longer suffix, and `--import motherload/register --import dotschema/register` loaded the schemas with dotschema, while the other order loaded them with Motherload's own schema loader (vendor `motherload`). Against the Motherload worktree whose schema loader was being removed, the same test passed in every order.
- **Tested** against a stand-in for Motherload's `.jsonc` loader written against the protocol alone (`tests/standin.ts`): in Node with both preloads in each order, in Bun with dotschema's preload adding its loader where the stand-in's plugin finds it, and in esbuild with both plugins in each order (`tests/interop.test.ts`); and against a real Motherload checkout when `MOTHERLOAD_DIR` names one (`tests/motherload.test.ts`, skipped otherwise): a project typed through both mappers, run under both preloads and bundled with both plugins, in each order.

## The types

A `.schema.jsonc` or `.schema.json5` file (`.schema.json` until 2026-10-19, [below](#the-suffix)) becomes the type the schema describes plus a validator (the maintainer's decision). The types come from an emitter of its own, `src/schema-types.ts` (the maintainer's decision of 2026-10-09, taken in Motherload). The alternatives were json-schema-to-typescript 16.0.0 (2026-08-28, 5.1 M weekly downloads), which compiles a schema to TypeScript declarations but installs 15.9 MB with its dependencies, prettier 9.96 MB of it, loaded every time ([Packaging](#packaging)); and json-schema-to-ts 3.1.1 (47 M weekly downloads, last release 2024-08-29, 0.47 MB with `@babel/runtime` and `ts-algebra`), which infers the type from the schema as a literal type, so the checker computes it again in every type check and each `$ref` is inlined.

- **No dependency:** the emitter is part of dotschema and needs nothing installed; only the validator needs ajv.
- **The root type is always `Type`,** whatever the root `title`, so `import { type Type as User }` works for every schema. An object root is an `interface`, any other root a `type`.
- **Each definition is a named type:** every entry of the root's `$defs` (or draft-07 `definitions`) is exported under its key in PascalCase (`my-tag` is `MyTag`; `Type2` when the name is taken), and a `$ref` to it is that name, so a recursive schema stays finite. The pointer `#` is `Type`; a pointer to anything else in the schema is inlined, and is `unknown` when it leads back into itself.
- **The keywords it reads:** `type` (one or a list), `properties` and `required` (an optional property is `a?: T | undefined`; a required key that `properties` does not list has the type of the `patternProperties` whose pattern matches it, or of `additionalProperties` when none does, [below](#the-types)), `additionalProperties`, `patternProperties` and `unevaluatedProperties: false` (an index signature, which also covers the named properties, as TypeScript requires, or none when closed; `unevaluatedProperties` closes the object only when no keyword beside it can allow another key: `allOf`, `anyOf`, `oneOf`, `if`/`then`/`else`, `dependentSchemas` or a `$ref`), `items`, `prefixItems`, `additionalItems` and `minItems` (an array, or a tuple whose positions from `minItems` on are optional), `const` and `enum` (literal types), `allOf` (an intersection), `anyOf` and `oneOf` (a union), `if`/`then`/`else` that test a property's listed values (a union, [below](#the-types)), and `description` (a doc comment). A keyword the schema's draft does not define is not read, `nullable` among them ([below](#the-validator)). Without `type`, the object keywords constrain an object and the array keywords an array, and every other JSON value passes them, so the type is that object or array or any other JSON value (`{ "properties": { "a": { "type": "string" } } }` is `{ a?: string | undefined; ... } | unknown[] | string | number | boolean | null`), the maintainer's answer of 2026-10-20: "It should have complete fidelity with what is allowed by the JSON schema itself." Until then such a schema was an object alone, though the validator accepted `5`. The JSON types a value can have come from `type`, `const`, `enum`, `allOf`, `anyOf`, `oneOf` and `$ref`, and a member of `allOf`, `anyOf` or `oneOf`, or a `then` or `else` read as an object, is read within its schema's: `{ "type": "object", "allOf": [{ "properties": ... }] }` is an object and that object, not a union of every JSON type. A schema should declare `"type": "object"` where it means one. A keyword that narrows a value no TypeScript type can express (`minLength`, `pattern`, `format`, `minimum`, `uniqueItems`) leaves the type as it is; `not`, `if`/`then`/`else` of any other shape and the other conditional keywords leave it wider. The validator checks all of them. Arrays and objects are mutable, as json-schema-to-typescript's were, except a `const` or `enum` value, which is typed as `as const` would type it.
- **The rule: the type admits every value the validator accepts.** Each keyword's type is meant to admit every value its rule does, and `allOf`, `anyOf` and `oneOf` compose those types as intersection and union, so a keyword the emitter does not read only widens the type. Checked against ajv on 2026-10-20 for `nullable` (the one keyword found where it did not hold: ajv honours OpenAPI 3.0's `nullable: true` and the type said `string`; the type then added `null`, and since the same day neither reads it, [below](#the-validator)), `$async` (ajv made the validator return a promise, which `.is()` took for a pass; ignored since), `if`/`then`/`else`, `dependentRequired` and `$dynamicRef` (each widens). An `unevaluatedProperties: false` beside `allOf` was recorded here as widening too, and did not hold: `{ "type": "object", "allOf": [{ "properties": { "a": { "type": "string" } } }], "unevaluatedProperties": false }` accepted `{ "a": "x" }`, and its type, `{ [key: string]: never } & { a?: string }`, refused it (measured on 2026-10-20 with tsc); since then it closes the object only when nothing beside it can allow a key (above). The test in `tests/schema-types.test.ts` assigns every sample ajv accepts to the type, for these schemas and the conditionals below, and runs tsc. A schema without `type` did not hold either until the same day (above): `{ "properties": { "a": { "type": "string" } }, "required": ["a"] }` accepted `5`, `"x"` and `null`, typed `{ a: string; ... }`, and `"address": { "properties": ... }` accepted `{ "address": 5 }`, typed as an object (measured); the test checks those too. A `$ref` beside other keywords is intersected with them in every draft, as ajv applies them in draft-07 too (measured on 2026-10-20: `{ "$ref": ..., "required": ["y"] }` refused an object without `y` under draft-07), though draft-07's text ignores a `$ref`'s siblings. Three more shapes did not hold, measured on 2026-10-20 and closed the same day, each checked by the same test:
  - **A required key that `properties` does not list,** beside `additionalProperties` or `patternProperties`, was `unknown`, which TypeScript refuses beside a narrower index signature: `{ "type": "object", "required": ["a"], "additionalProperties": { "type": "number" } }` gave `{ a: unknown; [key: string]: number }`, error TS2411 in the mapper's virtual code, so a valid schema failed the type check of every project that imported it. Such a key now has the type of every `patternProperties` entry whose pattern matches it (each applies, so their union admits it), tested as ajv tests a pattern (a Unicode regular expression, unanchored), or of `additionalProperties` when none matches, since a key a pattern matches is not an additional property; `never` when the object is closed and no pattern matches it, as no value then passes, and `unknown` without `additionalProperties`. A pattern this runtime cannot read adds `additionalProperties`' type too.
  - **An optional property was `a?: T`,** which under `exactOptionalPropertyTypes` refuses `{ a: undefined }`, while ajv passes a property that holds `undefined` as absent (it checks `data.a !== undefined`). It is now `a?: T | undefined`, which changes nothing without that option. JSON cannot hold `undefined`, so only a JavaScript value meets it. A required property that holds `undefined` is missing, for ajv and the type alike.
  - **An `$id` below a file's root is refused,** in the type check and the build, as a problem at that `$id`'s value (`embeddedIdProblems` in `src/refs.ts`), or at the root's reference to the file that holds it. ajv resolves a `$ref` inside such a schema against that `$id`, while the emitter resolves every pointer against the file: `{ "$defs": { "x": { "type": "string" }, "inner": { "$id": "https://example.com/inner", "$defs": { "x": { "type": "number" } }, "allOf": [{ "$ref": "#/$defs/x" }] } }, "allOf": [{ "$ref": "#/$defs/inner" }] }` validated `1` and refused `"s"`, typed `string`, in 2020-12 and in draft-07 with `definitions`; with the `$ref` beside the `$id`, ajv recursed until the stack ran out while compiling, reported as an invalid schema. The message names the fix: move that schema to a file of its own and `$ref` the file, or remove the `$id`. A plain-name `$id` (`"#name"`, draft-07's anchor) moves no base and stays, and so do the root's own `$id` and `$id` as data or as a property's name. Standard JSON Schema's conversion refused the same `$id`s already ([below](#standard-json-schema)); resolving each `$ref` against its `$id` in the emitter was the alternative.
- **The schema as written is a type of its own, `Json`:** the module declares `type Json = ` the schema's literal type and the default export as `Schema<Type, Json>`, so an error or a hover that names the module prints `Schema<Type, Json>`. With the literal inline it printed the schema itself, truncated (measured on 2026-10-20: `Type 'Schema<Type, { readonly $schema: "https://json-schema.org/draft/2020-12/schema"; readonly type: "object"; readonly properties: { ...; }; ... }>' is not assignable to type 'number'`). The type `Json` is not exported, since no consumer needs to name it: a library that re-exports a schema module still emits its declarations, TypeScript inlining the literal there (`tests/fixtures/declaration`, `tests/lab.test.ts`). A definition or another file's `Type` imported under that name takes another (`Json2`), as one named `Type` does.
- **Discriminated unions narrow:** a `oneOf` or `anyOf` of objects told apart by a `const` property is a union of object types with that property's literal type, and TypeScript narrows it in an `if` or a `switch`, exhaustively, also when the variants sit beside shared properties (an intersection with the union, which TypeScript distributes). The schema `lab/basic/event.schema.jsonc` is checked that way in `lab/basic/main.ts`. A union written with `if`/`then`/`else` narrows too, since the maintainer's pick of 2026-10-20: when an object schema's `if`, its own or that of each `allOf` member holding only a conditional, tests a required property with `const` or `enum` and nothing else, and that property's schema lists its values (`enum` or `const`, directly or through a `$ref` in the file), the conditionals are a union with one member per listed value, that value with the `then` of each test it passes and the `else` of each it fails. Every value the validator accepts has one of the listed values, so it is in that value's member, and the type stays as wide as the rule needs while TypeScript narrows on the property:

  ```jsonc
  { "type": "object", "properties": { "kind": { "enum": ["click", "visit"] } }, "required": ["kind"],
    "if": { "properties": { "kind": { "const": "click" } } },
    "then": { "properties": { "x": { "type": "number" } }, "required": ["x"] },
    "else": { "properties": { "url": { "type": "string" } }, "required": ["url"] } }
  ```

  is `{ kind: "click" | "visit"; ... } & (({ kind: "click" } & { x: number; ... }) | ({ kind: "visit" } & { url: string; ... }))`. One member per value, rather than each conditional typed as `(if & then) | else`, because an `else` cannot be typed without the complement of its `if`, and without it `(if & then) | unknown` is `unknown`; a chain of N conditionals in `allOf` would also be 2^N intersections for TypeScript to reduce. A property whose values are not listed (`{ "type": "string" }`), one that is not required, an `if` that tests two properties or anything beside `const` and `enum`, and a `$ref` to the values in another file are not read, and widen as before.
- **Compared with json-schema-to-typescript** on 19 schemas on 2026-10-09, by assignability both ways under tsc: the same type for 16. For the other 3, json-schema-to-typescript was wrong: it does not read `prefixItems`, so a 2020-12 tuple became `never[]` and an open one `[boolean, boolean, ...boolean[]]`, and it typed `{}`, which accepts every value, as an object.
- **A `$ref` to another schema file is that file's type,** imported from its module ([below](#references-to-other-files)); a `$ref` to a URL is not followed, and its type is `unknown`.
- **The schema itself is checked:** the type check compiles the schema with ajv and reports an invalid one (`tests/fixtures/errors`).

## References to other files

The maintainer's requirement of 2026-10-20: "We absolutely need to follow refs into other files." Built the same day, in `src/refs.ts` with the emitter and the validator.

```jsonc
// team.schema.jsonc, beside user.schema.jsonc and shared/place.schema.jsonc (lab/basic)
{ "properties": { "lead": { "$ref": "./user.schema.jsonc" }, "office": { "$ref": "./shared/place.schema.jsonc#/definitions/place" } } }
```

```ts
// Its module's types, as the mapper writes them:
import type { Type as User } from "./user.schema.jsonc";
import type { Place } from "./shared/place.schema.jsonc";
export interface Type {
  lead?: User;
  office?: Place;
  [key: string]: unknown;
}
```

- **Which file:** a reference's URI part is resolved against the file that holds it, as a relative URL, so `./user.schema.jsonc`, `user.schema.jsonc` and `../user.schema.jsonc` name files near it and a reference in another file resolves against that file. A `$id` does not move it: files are the unit, as TypeScript's imports are. A reference with a scheme of its own (`https:`, `urn:`, `file:`) is a URL and is not followed; ajv reports it, as before. The file must be a `.schema.jsonc` or `.schema.json5` file, so that its module is a schema's.
- **The type is an import of the other file's module,** so TypeScript sends that file through the mapper itself, with no `dynamicConfig` (measured with a probe mapper on 2026-10-20, Motherload's PLAN.md, "Content mapper facts"; `lab/basic/shared/place.schema.jsonc` is reached only this way, and its type is checked exactly in `lab/basic/main.ts`). A pointer to the file's root is its `Type`, imported under a name for the file (`./address.schema.jsonc` is `Address`); a pointer to an entry of its `$defs` or `definitions` is the type its module declares for it, under that name; a name taken in the importing module gets `2`, as a definition's does. A pointer to anything else is inlined from the other file, whose own references are imported in turn. Two files that refer to each other import each other, which TypeScript allows.
- **The importing module's text depends on the other file:** the names it imports and what it inlines. TypeScript transformed every mapped file on every `--incremental` run and on every change under `--watch` (measured on `7.1.0-dev.20261002.1`, Motherload's PLAN.md, "Content mapper facts"), so the text is never stale on that build.
- **The validator is compiled from every file the schema reaches,** transitively, in one ajv instance: each other file is added with `.addSchema()` and the root compiled, so a cycle between files validates. The module still imports nothing, and `schema` is the root file's own schema, its references as written.
- **No path in the module:** ajv's standalone code embeds each schema's `$id` (measured: with file URLs as ids, the module held the absolute path four times). Each file is given an id with no path, its own `$id` when that has a scheme and `dotschema:<n>` otherwise (`motherload:<n>` until the extraction), and each reference to another of the files is rewritten to that file's id, keyword by keyword (`properties`, `items`, `allOf` and the rest), so data under `const`, `enum`, `default` or `examples` that holds a `$ref` key stays as written (`tests/schema.test.ts` checks that the module holds no part of its directory's path).
- **One draft:** every file is compiled in the root's draft. A file that declares another `$schema` than the root's (drafts 06 and 07 count as one) is a problem; a file that declares none is read in the root's.
- **Problems are placed at the reference** in the root's text: a file that does not exist, cannot be read or does not parse, a file that is not a schema file, a pointer to nothing (`#/$defs/nope`), a draft that differs. A problem in a file the root reaches through another is placed at the root's reference to that file, its message prefixed with the file (`./via.schema.jsonc: The $ref ...`). The reference's type is `unknown`, so the problem is the one error. A referenced file's own problems are also reported in that file, which the import brings into the program (`tests/fixtures/errors/broken-ref.schema.jsonc` is reported at line 4, column 35).
- **Bundlers rebuild on a change to a referenced file:** the loader's `load` returns the files it read as `watchFiles`, which the esbuild plugin passes on, also when the module fails, so creating a missing file rebuilds it (`tests/adapters.test.ts`). The esbuild bundle of `lab/basic` counts `team.schema.jsonc` as one input: the files it refers to are compiled into its validator. The Node and Bun preloads build each module once and watch nothing.
- **Nothing is shared or cached between modules,** the maintainer's question of 2026-10-20 ("if there's a bunch of imported schemas that all reference some shared schema"): each module reads, parses and compiles every file it reaches, and carries its own compiled copy of them. Measured that day with ten schemas that each refer twice to one shared schema of six properties (`pattern`, `email`, `date-time`), against one: a module built in 7 ms once ajv was loaded (40 ms for the first, which loads it), `tsc` took 377 ms against 315 ms, and the esbuild bundle was 188 KB minified (6.3 KB gzipped) against 18.8 KB (3.8 KB), growing with each schema. So caching the compile by path would save milliseconds, and was not added; the size is the cost. Of a module's bytes, a schema of `type: "string"` alone is 1.3 KB minified, and a `format` ajv-formats checks with a function (`date-time`) adds 7.4 KB, because ajv's standalone code requires ajv-formats' whole formats module, which is inlined whole (a regular-expression format such as `email` adds 0.3 KB). Sharing would mean modules that import the modules of the files they refer to and call their validators, which ajv's standalone code cannot link ([PLAN.md](./PLAN.md#open)).

## The suffix

A schema file's suffix is `.schema.jsonc` or `.schema.json5`, and the suffix names the dialect the file is read in (the maintainer's decisions of 2026-10-20: `.schema.jsonc` in the morning, then `.schema.json5` beside it, "I think we can continue supporting it for .schema.jsonc and .schema.json5. Kind of nice to be able to have comments as well."). It was `.schema.json` until 2026-10-19, then `.jsonschema` for a day (the maintainer's answer of 2026-10-19, replaced on 2026-10-20). [microsoft/TypeScript#64581](https://github.com/microsoft/TypeScript/pull/64581), merged 2026-10-13, refuses a content mapper extension that ends in a built-in one with the TS18066 that `.json` itself gets, and the `release-7.1` branch, cut as `7.1.0-beta` on 2026-10-16, carries it. Measured on 2026-10-19 with a tsconfig registering `.schema.json`, `.sql` and `.pg.sql` for a probe mapper: `7.1.0-dev.20260929.1` accepted all three, and `7.1.0-dev.20261019.1` reported `TS18066: Content mapper file extension '.schema.json' is a built-in extension and cannot be registered by a content mapper` and accepted the other two. The pinned `7.1.0-dev.20261002.1` predates the rule.

## The validator

```ts
import user, { type Type as User } from "./user.schema.jsonc";
user.validate(input);           // { value: input }, or { issues } with every issue; never throws
user.is(input);                 // input is User, stopping at the first failure
user["~standard"].validate(x);  // Standard Schema v1: the same function as validate
user["~standard"].jsonSchema;   // Standard JSON Schema v1, below
user.schema;                    // the JSON Schema, typed as a literal
```

- **The `.validate()` and `.is()` methods, and nothing that throws,** the maintainer's decision of 2026-10-20: "We should not provide any method that throws an error. Does AJV not let you produce a complete array of issues, or does it? In my opinion, there should be a `validate` method that returns complete error information, and then the `is` method can return at the first failure and give you back a boolean and/or act as a type guard. Why don't you write all this up as a TypeScript interface?" The interface was written, and the answer was "Build it as written". The `.validate(value)` method returns Standard Schema's result with dotschema's issues, `SchemaResult<T>`: `{ value }`, the value it was given, the same object, or `{ issues }`, every issue, typed as a tuple of at least one; `~standard.validate` is the same function (`user.validate === user["~standard"].validate`), so a Standard Schema library gets the same issues. The `.is(value)` method is a type guard. The `schema` property is the schema as written, its `$ref`s to other files and the keywords dotschema ignores (`nullable`, `$async`) included, so a tool that wants the schema to `~standard.jsonSchema.input({ target })`, which is self-contained and leaves those keywords out. Nothing on the module throws but `~standard.jsonSchema` for a target it cannot produce, which Standard JSON Schema requires ([below](#standard-json-schema)); where ajv itself throws, both methods answer instead (below). The package exports `SchemaResult` and `SchemaIssue` beside `Schema`. In the type, `~standard`'s own `.validate()` comes first in the intersection with Standard Schema's props, so that `user["~standard"].validate(x)` is typed `SchemaResult<T>`: with Standard Schema's first, the call took its signature, a result or a promise of one (measured with tsc on 2026-10-20). The alternatives: `.parse()`, the module's method until that day, which returned the value or threw a `TypeError` carrying the issues (a `SchemaError` in the types), and which the maintainer's rule takes out because it throws; and one validator for both methods, with `allErrors`, which is smaller, but `.is()` would go on checking a value it already knows fails, where the maintainer asked that it "return at the first failure".
- **Two validators in one module:** ajv sets `allErrors` per instance, so the module is built with two, one with `allErrors` for `.validate()` and one without for `.is()`, each compiled from the same files with the same formats, meta-schemas and ignored keywords (`loadAjv` and `compile` in `src/schema.ts`, run once for each). Their standalone codes are inlined into one module that shares one table of run-time modules, so a helper both require (ajv's `ucs2length`, fast-deep-equal, ajv-formats' formats) is in it once (`tests/schema.test.ts`). The `.is()` method uses the second: on an object whose first property fails, it returns without reading the next one, which `.validate()` reads (a getter that counts, in the test). What the second costs, measured on 2026-10-20: `lab/basic/user.schema.jsonc`'s module grew from 8,544 to 14,573 bytes (2,601 to 3,402 gzipped), and `lab/basic/event.schema.jsonc`'s, which carries ajv-formats' formats, from 21,916 to 29,985 (5,582 to 6,518 gzipped). Tests in `tests/json-schema.test.ts` check that the two agree on every value it tries, and `tests/verdicts.test.ts` on generated values (JSON's kinds, empty and nested-empty arrays and objects, the schema's own literals, objects of the property names it mentions) for every schema in the labs and the fixtures and a list of its own.
- **The `.is()` method confirms a pass where ajv's first-failure code is wrong** (the maintainer, 2026-10-20: "Do option B, but this is something that we should make a note of for when we eventually vendor AJV"). ajv 8.20.0's validator without `allErrors` accepts `[]` for `contains` beside a tuple, which the schema refuses and the validator with `allErrors` refuses: `{ "prefixItems": [{ "type": "string" }], "contains": { "type": "number" } }` in 2020-12, a draft-07 list of `items` with `contains`, and either nested in a property (measured; draft-07's `prefixItems`, which draft-07 ignores, does not). The cause, read in the code ajv generates: `prefixItems` sets the validity it gates the next keyword on only inside `if (len0 > 0)`, so for an empty array it stays `undefined` and `contains` never runs; with `allErrors` the keywords are not gated on each other. Not reported to ajv (its issues and pull requests searched on 2026-10-20; the nearest, ajv-validator/ajv#502, is a 2017 ajv 5 bug, fixed), and 8.20.0 is its latest release. So when the build finds `contains` beside `prefixItems` or a list of `items` in any file the validator is compiled from (`needsConfirmation` in `src/schema.ts`), the module's `__confirm` is `true` and `.is()` checks a pass again with `.validate()`'s validator; otherwise `.is()` is the first validator alone. The alternative was one validator for both, which costs every `.is()` the full check; the guard goes when the validator is dotschema's own ([PLAN.md](./PLAN.md#open)).
- **An issue** (`SchemaIssue`) is `{ message, path, keyword }`: ajv's `message`, the `path` in the value and the `keyword` that failed. The maintainer's answer of 2026-10-20 on ajv's `params` and `schemaPath`, which it carried until then: "Drop both". ajv's `schemaPath` pointed at the wrong place across `$ref`s and files: it is relative to the compiled function that raised the error, so an error in a recursive `$defs/node` read `#/properties/name/type`, which is not at the root, and one in another file read as an internal id (`motherload:1/properties/name/type`, `dotschema:1/...` since the extraction) or as the root's own (measured in the review of the interface). And anything an issue carries, a validator of dotschema's own would have to reproduce, while a field can be added later without breaking anyone. The path holds object keys as strings and array indexes as numbers. ajv's `instancePath` is a JSON Pointer, which writes an index as it writes a key (`/0` either way), so each unescaped segment is read against the value it names: under an array a number, under anything else a string, so `{ "map": { "0": 1 } }` gives `["map", "0"]` and `{ "list": [1] }` gives `["list", 0]`. The key of a property that ajv names in the error's params ends the path, so an issue about a property points at it whether or not it is there: `required`'s, `dependentRequired`'s and draft-07 `dependencies`'s `missingProperty` (one issue per missing property, as ajv reports them), `additionalProperties`' `additionalProperty`, `unevaluatedProperties`' `unevaluatedProperty`, and `propertyNames`' `propertyName`, the key whose name fails. ajv reports the name's own failure (`pattern`, say) first, with the key on the error itself (`error.propertyName`) and not in its params, and that key ends its path too, so both issues point at the key. The discriminator's error (below) ends at the tag, its key, and is reported with the keyword `oneOf`, which the schema holds, and not `discriminator`, which dotschema added. The keywords `items: false`, `additionalItems` and `unevaluatedItems` give a `limit` and no index, so their path ends at the array. Reading the value again runs a getter once more (ajv reads a property twice, so the walk is its third read); a read that throws then leaves the rest of the pointer as keys, rather than making `.validate()` throw.
- **Nothing changes the value:** the package sets none of ajv's options that write to it (`useDefaults`, `coerceTypes`, `removeAdditional`), so a `default` is not filled in (and the type keeps a property with one optional), `"1"` is not made a number and an extra property is not removed, and the value `.validate()` returns is the object it was given, as it was given (`tests/schema.test.ts`).
- **Where ajv itself throws, neither method does:** the maintainer's rule, "We should not provide any method that throws an error", holds for every value. ajv's code throws for some (measured on 2026-10-20): `JSON.parse` of 3,000 nested arrays, 6 KB of text, against a recursive schema for any JSON value ran until the stack was exhausted, a `RangeError`, as did a value that refers to itself where a recursive schema descends into it, `uniqueItems` over two such values (fast-deep-equal recursing) and 100,000 levels of nesting; a getter that throws while ajv reads it threw its error, and a revoked proxy threw `TypeError: Cannot perform 'IsArray' on a proxy that has been revoked`. Each validator is called inside a `try`: `.is()` returns `false`, since the value is not known to be valid, and `.validate()` returns one issue at the root, `{ message: "could not be checked: " + the error's message, path: [], keyword: "error" }` (`tests/schema.test.ts`). The same holds for ajv-validator/ajv#2624 (open): an object whose `valueOf` is not a function, against an object in `enum` or `const`, made ajv throw `a.valueOf is not a function` (measured). The alternative was to let the throw through and document it, which the review that measured the 6 KB case argued against: a handler that calls `user.validate(JSON.parse(body))` is told it can rely on no throw. Until then, from 2026-10-20 when `.validate()` replaced `.parse()`, both methods let ajv's error through. Other values that are not JSON are refused or accepted by ajv's rules without a throw (`undefined`, a symbol, a function, a `BigInt`, `NaN`, a `Map`, an object with no prototype, a proxy); one is accepted where JSON has no such value: ajv's `integer` test lets `Infinity` through (`Infinity % 1` is `NaN`, which its `!(x % 1)` reads as an integer).
- **The ajv validator, a dependency of dotschema's** (the maintainer's decision names ajv). Version 8.20.0 (2026-04-24, 464 M weekly downloads) validates drafts 06, 07, 2019-09 and 2020-12; the draft comes from `$schema` (`ajv/dist/2019`, `ajv/dist/2020`), and draft-04, draft-03 and any other `$schema` (OpenAPI 3.1's dialect among them) are refused with a diagnostic, in the type check as well as the build since 2026-10-20 (the type check passed them until then, and the build failed). Draft-06 takes ajv's draft-06 meta-schema (`ajv/dist/refs/json-schema-draft-06.json`), which ajv's default class lacks; until 2026-10-20 a draft-06 schema failed with `no schema with key or ref "http://json-schema.org/draft-06/schema#"` (measured). ajv-formats, also a dependency, validates `format`. Both are resolved from dotschema's own module, not from the schema's directory, because under pnpm a package's dependencies resolve from the package only (`tests/schema.test.ts` builds a schema in a directory with no `node_modules`).
- **A schema with no `$schema` is draft-07,** ajv's default class, as it always was; asked on 2026-10-20 whether such a schema should be supported, it is, since many schemas omit the keyword (the README's own example does). What changed that day: ajv ignores a later draft's keyword in an earlier draft without a word, while the emitter read it whatever the draft, so the type said more than the validator checked (measured: with no `$schema`, `prefixItems: [{ "type": "string" }]` let `[1]` through, typed `[string?, ...unknown[]]`). Measured on 2026-10-20, draft-07 ignores `prefixItems`, `unevaluatedProperties`, `unevaluatedItems`, `dependentRequired`, `dependentSchemas`, `minContains`, `maxContains`, `$dynamicRef` and `$recursiveRef`, and 2019-09 ignores `prefixItems`. The emitter now reads `prefixItems`, a list of `items` with `additionalItems`, and `unevaluatedProperties` only in the drafts that have them, so the type is what the validator checks, and without `type` only an array keyword the draft reads makes an array. For a few hours that day each such keyword was also an error at its key naming the `$schema` to declare; the maintainer's instruction that a keyword a schema's draft does not define is ignored ([below](#the-validator)) took it out. A warning in its place is not possible: TypeScript 7.1 (`7.1.0-dev.20261002.1`) shows every content mapper diagnostic as an error and exits 2, whatever `category` (`"warning"`, `0`, `"suggestion"`, `"message"`) or `severity` it carries (measured with a mapper of its own). The alternatives were 2020-12 for a schema with no `$schema` (the current draft, though a draft-07 schema that omits the keyword and writes a tuple as a list of `items` would then be refused as invalid) and inferring the draft from the keywords used.
- **Dependencies, not optional peers:** ajv and ajv-formats were Motherload's optional peers until 2026-10-20, as the maintainer's decision of 2026-10-03 had it, so that a project with no schema installed no validator. The maintainer asked on 2026-10-20 why ajv alone was optional: it was not Motherload's largest dependency (csv-parse is 1.61 MB, ajv and ajv-formats 1.09 MB together), and the package family decided on 2026-10-09 gave ajv to `@motherload/schema` as dependencies. The maintainer's reason for a dependency over a peer, the same day: "later on we could move away from AJV without breaking people", since a project never names ajv itself. Since the extraction, a project that wants no validator does not install dotschema.
- **Compiled when the module is built,** with ajv's standalone code, so the module needs no validator library at run time and no `new Function`. Measured: standalone code `require`s run-time helpers (`ajv/dist/runtime/ucs2length` for `minLength`, `equal` for `uniqueItems` over objects), even with `code: { esm: true }`; dotschema inlines each required CommonJS module, transitively, into the module, so the generated module imports nothing. The standalone code's requires resolve from the schema package's own module, where ajv and ajv-formats are both dependencies: until 2026-10-20 they resolved from ajv's directory, where ajv-formats does not, so a format ajv-formats checks with a function (`date-time` and `uri` among them; `email` is a regular expression, inlined as one) stayed a bare `require("ajv-formats/dist/formats")`, and the module threw `require is not defined` when it ran (measured, in every draft; `lab/basic/event.schema.jsonc` checks `date-time` and `uri`). The esbuild bundle of `lab/basic` has no `node_modules` input and runs with nothing installed (`tests/lab.test.ts`).
- **One copy of ajv compiles the schema and writes every format's code,** dotschema's own, at the version `dist` pins (8.20.0). ajv-formats' plugin writes the formats' code with the codegen of the ajv its own `require("ajv")` finds, and a copy of ajv takes only its own copy's code for code. Measured on 2026-10-20: under npm 11.20.0 beside eslint 10.13.0 (which depends on `ajv ^6.14.0`), and under nub's hoisted layout beside ajv 6.12.6, ajv 6 sat at the top and ajv 8.20.0 twice below it, under `@motherload/schema` (under `dotschema` since the extraction) and under `ajv-formats`. The compiling copy wrote ajv-formats' code out as JSON (`const formats2 = {"_items":[…]}.uri`), so every format ajv-formats checks with a function, and `formatMinimum`, `formatMaximum` and the exclusive pair, threw when they ran (`formats2 is not a function`), under the preload and in every bundle alike, while the type check passed. So `loadAjv` registers ajv-formats' plain format table (`ajv-formats/dist/formats`, which requires nothing) with dotschema's ajv, sets `code.formats` with that ajv's codegen as the plugin would, and writes the four limit keywords with it (`formatLimits`, after ajv-formats' `dist/limit.js`, without `$data`, which dotschema does not enable). Tests in `tests/schema.test.ts` check every format and the limit keywords against ajv-formats' own plugin, and `scripts/check-dist.ts` installs `lab/basic` hoisted beside ajv 6. The alternatives, both measured: compiling with the ajv found from ajv-formats' own directory (one line, and every layout passed, but under npm that copy is whatever `^8.0.0` resolved to, not the pinned version); and the package's own ajv with only `code.formats` set (the formats passed, the limit keywords still threw `….compare is not a function`).
- **Only a double-quoted `require` in ajv's standalone code is inlined,** and one that does not resolve, or names a Node.js built-in, is a problem, never a bare `require` left in the module. The standalone code holds the schema's own strings, which ajv writes with `JSON.stringify`, which escapes `"` and not `'`. Until 2026-10-20 the inliner's regex took a single-quoted `require('…')` in a string for a call (measured): `"const": "load require('ajv/dist/runtime/equal') now"` became `"load __require(0) now"` in the validator, which then refused the one value the schema allows; a property named `require('ajv')` gave the issue path `["__require(3)"]` and inlined all of ajv (126 KB minified); `require('fs')` failed the build with `ENOENT`; `require('./refs.js')` pasted the package's own ES module into the module, a `SyntaxError` when it loaded; and `require('fast-uri')` in a string was rewritten or not depending on whether the install layout made fast-uri resolvable from the schema package. ajv writes its helpers' requires with double quotes, and a `"` in a string is always `\"`, so the standalone code is read for `require("…")` alone. An inlined helper's own source keeps the general pattern (fast-uri writes `require('./lib/utils')`).
- **A process that disallows code generation from strings cannot build a schema module:** ajv compiles every validator with `new Function`, the one it writes out as standalone code too, so under `--disallow-code-generation-from-strings` (on the command line or in `NODE_OPTIONS`, which reaches the mapper process too) the preload and the type check refuse every schema. Until 2026-10-20 some said "The schema is not valid: Code generation from strings disallowed for this context" and others threw it uncaught (measured); the problem now says what happened and that a module built in a process without the flag, as an esbuild bundle is, validates where the flag is set (measured: the bundle of every test schema ran under the flag with the same verdicts).
- **Options:** `allErrors: true` for `.validate()`'s validator, so a failure lists every issue, and not for `.is()`'s, so it stops at the first; `strict: false` and no logger in both, so a schema written for another validator still compiles.
- **Two of ajv's defaults are changed, so that the validator checks the schema as written, no stricter** (the maintainer's "complete fidelity with what is allowed by the JSON schema itself", [Types](#the-types)); both are set on every ajv instance dotschema makes for a schema, the two validators and the type check's compile, since 2026-10-20. **The `ownProperties: true` option:** by default ajv reads a property through the prototype, so `{}` failed `properties: { toString: { type: "string" } }`, `Object.prototype.toString` being a function, and passed `required: ["toString"]` (measured); a JSON value's properties are its own, and with the option a property is one only when it is the value's own, which also leaves an inherited key out of `additionalProperties`. **The `multipleOfPrecision: 7` option:** by default ajv tests `multipleOf` as `x / m` being an integer in binary floating point, so it refused `19.99` and `0.07` for `0.01`, and `0.3` and `0.7` for `0.1`, whose quotients a double misses by about 1e-13 (measured), while the schema means the decimals as written. With a precision `p`, ajv takes `x` as a multiple when `x / m` is within `10^-p` of an integer, a fixed tolerance, while a double's error in the quotient grows with it, about `q × 3e-16`: so a larger `p` refuses true multiples sooner as the quotient grows, and a smaller one lets more values just off a multiple through. Measured on 2026-10-20 over 2.7 million written multiples per range (nine steps from `0.01` to `2.5e-5`, each value as JSON writes it): `p = 9` refused none below a quotient of 10^6 and 3% between 10^6 and 10^7 (`863807.2` for `0.1`); `8` none below 10^7 (`932179.19` for `0.01` refused above it); `7` none below 10^8; `6` none below 10^9. The value `7` is chosen: every amount under a million in cents, or under ten million in tenths, is read exactly, and a value counts as a multiple only within a ten-millionth of a step, so `0.015` and `0.005` are still refused for `0.01` and `0.35` for `0.1`, while `0.1 + 0.2` (`0.30000000000000004`) is a multiple of `0.01`. The review that found it proposed `9`, which refuses `146153.02` for `0.01`. Integers are unaffected for quotients a double holds exactly.
- **Only the matching variant's issues** (the maintainer's pick of 2026-10-20). For a `oneOf`, ajv with `allErrors` reports every variant's failures and the `oneOf`'s own: `{ "kind": "click", "x": 1 }` against `lab/basic/event.schema.jsonc` gave five issues, `required 'url'` and the visit's `const` on `kind` among them, which say nothing about a click. ajv's `discriminator` keyword (with its `discriminator: true` option) validates only the variant a property's value names, and gives exactly `required 'at'` and `required 'y'`. The package adds `discriminator: { propertyName }` to the copy ajv compiles, never to the module's `schema` or its Standard JSON Schema, where ajv 8.20.0's rules hold (`dist/vocabularies/discriminator/index.js`) and the verdict is the `oneOf`'s (`withDiscriminators` in `src/schema.ts`): the schema beside the `oneOf` is `type: "object"`, since ajv skips the `oneOf` beside a discriminator and checks the tag only on objects, so without it `5` and `null` passed where the `oneOf` refuses them (measured); each variant, or the schema a variant that is only a `$ref` points to, in the file or another, has the property in its own `properties` with a `const` that is a non-empty string (ajv reads `""` as no `const` and refuses the schema) or an `enum` of one string, the values distinct; the property is required beside the `oneOf` or in every variant; and no file the validator is compiled from uses `unevaluatedProperties` or `unevaluatedItems`, since ajv's discriminator does not pass on what its variant evaluated (measured: `{ "kind": "y" }` failed `unevaluatedProperties: false` beside such a `oneOf`, which passes it without the discriminator). Then a value whose tag names one variant fails every other on the tag, so the `oneOf` holds exactly when that variant does. A tag that is not a string, or names no variant, is one more issue at the tag. A `discriminator` the schema holds itself (OpenAPI's) is taken out of the copy, as ajv without the option ignored it. Were ajv to refuse an added one, the validator is compiled without any. Tests in `tests/verdicts.test.ts` check the event's issues, an unknown and a non-string tag, a variant through a `$ref` in the file and in another, a nested union, each shape left alone, and that the verdicts equal those of the `oneOf` compiled as written on generated values. Elsewhere a `oneOf` or `anyOf` keeps ajv's flat list of every variant's issues. The alternatives: the flat list as it was, and keeping only the issues of the variant that failed least, which needs a rule of dotschema's own for "least".
- **Where ajv is more lenient than the spec, not fixed:** in 2020-12, ajv takes every item of an array as evaluated once `contains` is present, where the spec counts only the items `contains` matched (core 11.2): with `contains: { type: "number" }` and `unevaluatedItems: { type: "boolean" }`, ajv accepted `[1, "x"]` and `["x", 1]`, which the spec refuses for `"x"` (measured on 2026-10-20, with and without `allErrors`). The type is not affected: the emitter reads neither keyword, so that schema is typed `unknown[]` (measured).
- **A keyword the schema's draft does not define is ignored,** by the validator and by the type, as the spec ignores it. The maintainer's instruction of 2026-10-20: "I want to make sure that any unrecognized keywords that show up inside the JSON schema file are ignored. That's technically valid, but I want to say that sometimes AJV is overly strict with this." ajv's strict mode is off (`strict: false`), so a vendor's keyword (`x-foo`, `tsType`, `errorMessage`, `markdownDescription`), an unknown format, and an unknown keyword that holds a `$ref` to a missing file compiled and were ignored in every draft already (measured that day, `tests/schema.test.ts`). What was not ignored: the keywords ajv itself acts on beyond the draft, read from ajv 8.20.0's vocabulary for each class (`dist/vocabularies/draft7.js`, `draft2020.js`, `dist/2019.js`, `dist/core.js`) and measured. Setting `$async: true` made the validator return a promise, which `.is()` took for a pass, and one nested in a property made ajv refuse the schema; OpenAPI 3.0's `nullable` made ajv refuse a schema without `type`, a value that is not a boolean, and `type: ["string", "null"]` beside `nullable: false`; draft-04's `id` was refused (`NOT SUPPORTED: keyword "id"`); ajv's 2019-09 class enforces 2020-12's `$dynamicRef` and `$dynamicAnchor`, its 2020-12 class refused 2019-09's `$recursiveAnchor: true`, and both enforce draft-07's `dependencies`, which 2019-09 replaced. Those are taken out of what ajv compiles and what the emitter reads (`IGNORED` in `src/schema.ts`): `$async`, `nullable` and `id` in every draft, `$dynamicRef`, `$dynamicAnchor` and `dependencies` in 2019-09, `$recursiveRef`, `$recursiveAnchor` and `dependencies` in 2020-12, in the schema and in every file it refers to, keyword by keyword, so a property named `id` and a `const` that holds one keep it. The schema the module exports, and its literal type, stay as written. Every other keyword a draft does not define, a later draft's included, ajv ignores already, and so does the emitter. Draft-06 is compiled as draft-07, so ajv enforces `if`, `then` and `else` in it, though draft-06 does not define them (measured: `{ "if": { "const": 1 }, "then": false }` refused `1`). A keyword a draft defines with a value its meta-schema refuses (`"title": 5`, `"examples": {}`) is still an invalid schema, as before.
- **A 2020-12 `$dynamicRef` that ajv resolves to the root is refused,** at the reference, in the type check and the build. ajv 8.20.0 resolves `"#name"` to the `$dynamicAnchor` of that name only when it has compiled one already, and otherwise, as for a JSON Pointer (`"#/$defs/s"`), to the root of the schema; its own source says as much (`dist/vocabularies/dynamic/dynamicRef.js`: "the assumption here is that `recursiveRef: #` always points to the root"). Measured on 2026-10-20 against the spec's answers: with `"$dynamicAnchor": "content"` in `$defs` and `"items": { "$dynamicRef": "#content" }`, the validator checked each item against the root, refusing `["a"]` and accepting `[[]]`; with the reference at the root it recursed until the stack ran out, on every value; a JSON Pointer refused what its target accepts. An anchor at the root of the file, or of a schema with an `$id`, was resolved as the spec says, the extending schema's own anchor included, so those compile (`dynamicRefProblems` in `src/refs.ts`; `tests/schema.test.ts`); an `$id` below a file's root is refused since the same day ([types](#the-types)), so the message names the fix that remains: declare the anchor at the root of the schema, or write the reference as a `$ref`. The type is not affected: the emitter does not read `$dynamicRef`, so its type is `unknown`.
- **Standard Schema v1:** the default export implements `~standard` (vendor `dotschema`, `motherload` until the extraction) for any library that accepts one; the interface is copied into `src/index.ts`, so the types depend on no package. The brand study's consequence that "a module that exposes `~standard` plugs into every Standard Schema consumer" is the reason.
- **The module imports nothing from dotschema,** so dotschema stays a development dependency of an application that bundles (the condition Motherload took from the porg repository's `docs/brands.md`); the generated `.ts` text imports types from `dotschema`, which the type check resolves ([Packaging](#packaging)).

## Standard JSON Schema

The schema module implements Standard JSON Schema v1 (`@standard-schema/spec` 1.1.0, 2025-12-15) for the `"draft-07"` and `"draft-2020-12"` targets, the two the spec "strongly recommends" (the maintainer's answer of 2026-10-20: "Yes, draft-07 and 2020-12"). A library that needs a schema as JSON Schema (an API or tool definition) reads it from `~standard.jsonSchema`:

```ts
user["~standard"].jsonSchema.input({ target: "draft-2020-12" }); // { $schema: "https://json-schema.org/draft/2020-12/schema", ... }
user["~standard"].jsonSchema.output({ target: "draft-07" });     // the same schema as input: nothing transforms the value
user["~standard"].jsonSchema.input({ target: "openapi-3.0" });   // throws, as the spec asks of a target the library does not support
```

- **Computed when the module is built** (`src/json-schema.ts`, called from `schemaCode`): the module carries each target's schema, or the reason it has none, and returns a fresh copy (`structuredClone`) on each call, so a caller may change it. The `.input()` and `.output()` methods return the same schema, since validation never changes the value.
- **Self-contained:** every other file the schema reaches through a `$ref` is folded in under the target's container (`$defs` in 2020-12, `definitions` in draft-07), keyed by its name without the suffix (`user`, `user2` when taken), and every `$ref` becomes a JSON Pointer into the one document: `lab/basic/team.schema.jsonc`'s `lead` is `#/$defs/user` in 2020-12 and `#/definitions/user` in draft-07. A folded file loses its `$schema` and `$id`; a reference to a file's absolute `$id` becomes a pointer too; a URL `$ref` is left as written. This is not 2020-12's bundling (core 9.3.1), which keeps each file's `$id` and its references as written: the verdicts are the same, and the schema paths of errors differ.
- **Converted where the two drafts say the same thing:** `definitions` and `$defs`; a list of `items` with `additionalItems` and `prefixItems` with `items`; `dependencies` and `dependentRequired`/`dependentSchemas` (a property in both is `{ allOf: [{ required }, schema] }` in draft-07); a draft-07 `$id: "#name"` and `$anchor`, every reference to an anchor becoming a pointer. Draft-07 ignores the keywords beside a `$ref` (core 8.3) while ajv and the later drafts apply them, so going to draft-07 a `$ref` with validating keywords beside it moves into `allOf`. A keyword the schema's own draft does not define (`prefixItems` in a draft-07 schema, which ajv ignored) is left out of both targets, so the target does not start applying it; a vendor keyword (`x-foo`) is kept.
- **Refused rather than approximated:** where a keyword has no exact equivalent in the target, that target throws with the keyword and its place (`./file#/pointer`), and the other target still converts. To draft-07: `unevaluatedProperties`, `unevaluatedItems`, `minContains`/`maxContains` beside `contains`, `$dynamicRef`/`$dynamicAnchor`, `$recursiveRef`/`$recursiveAnchor`. From 2019-09 to 2020-12: `$recursiveRef`/`$recursiveAnchor`, and `unevaluatedItems` in a schema that uses `contains`, which 2020-12 counts as evaluating items and 2019-09 does not (2020-12 core 11.2). In 2020-12, `$dynamicRef`/`$dynamicAnchor` across several files, whose resolution one document does not keep apart. In both: an `$id` inside a file (which the module refuses before the conversion, [types](#the-types)), a root `$id` with a fragment, a `$ref` to something that is not a schema the conversion places, and one name in both `definitions` and `$defs`.
- **Checked by equivalence** (`tests/json-schema.test.ts`): for each produced schema, ajv compiling it for its target (`ajv` or `ajv/dist/2020`, with `allErrors`, ajv-formats and `strictSchema`, so a keyword the target would ignore fails the compile) gives the same verdict as the module's own validator on valid and invalid values, for the fixtures in `tests/fixtures/json-schema/` (2020-12, draft-07 and 2019-09, across files, with anchors, tuples and both kinds of dependency) and for `lab/basic`'s schemas; `lab/basic` prints `team`'s two conversions under the preload and from the esbuild bundle.
- **Not verified:** equivalence is measured with ajv alone, so that a draft-07 reader ignores a `$ref`'s siblings is covered by the shape of the output, not by a second validator; `format` is carried as written, which ajv-formats asserts in both drafts and a default 2020-12 validator treats as an annotation.


## Diagnostics

- **Shown as `dotschema<code>`:** the mapper answers `initialize` with `diagnosticSource: "dotschema"`. Codes: 1 a syntax error, 3 a file whose suffix dotschema does not read (a tsconfig entry listing another extension), 4 the schema, 5 an option in tsconfig; Motherload's numbers, of which 2 has no case here ([above](#the-extraction-from-motherload)).
- **Positions are UTF-8 bytes.** The mapper declares `positionEncoding: "utf-8"` and converts the parsers' UTF-16 offsets (`utf8Range`), as Motherload's does (`tests/mapper.test.ts` places an error after an `é`).
- **A schema that does not parse is typed `any`,** `Type` included, so the diagnostic in the file is the one error and every use of the import stays quiet.

## The mapper process

As in Motherload (its DESIGN.md, "The mapper process"):

- **No `dynamicConfig`.** A schema's module depends on its file, the files it refers to and ajv. A `$ref` to another file keeps the flag off, because the types import that file's module, which TypeScript follows itself ([above](#references-to-other-files)). Without the flag TypeScript starts the process only for a matching file.
- **No options.** A key in a tsconfig entry's `options` is reported (code 5) through `optionDiagnostics`.
- **An `.mts` module:** the mapper reports each module as `.mts`, an ES module whatever the nearest `package.json` says, as the preload and the plugin load it.

## Releasing

The package is released by `.github/workflows/release.yml`, Motherload's release (Motherload's DESIGN.md, "Releasing"), which is Zod's, for one package in place of Motherload's ten. The maintainer asked on 2026-10-21 for the repository to be "Public, with Motherload's release workflow"; it is public at colinhacks/dotschema, with `main` its default branch (`gh api repos/colinhacks/dotschema`, read on 2026-10-21).

- **The same as Motherload's:** the workflow runs on `gh workflow run release.yml -R colinhacks/dotschema` and from `main` alone, never on a push or a tag, so a version bump on `main` publishes nothing by itself. Its `test` job runs `nub run typecheck`, `nub run test`, `nub run build` and `nub run check-dist`; its `stage` job, on the `npm` environment with `id-token: write`, installs npm 11 (`npm stage` needs 11.15), builds and runs `check-dist` again, and stages `dist/dotschema` with `npm stage publish --provenance --access public` through `.github/scripts/npm-stage-publish.sh`, authenticated by OIDC with no npm token; its `approval` job, on the `release-approval` environment, holds the run with no runner for up to 30 days; and its `finish` job waits up to 340 minutes for npm to serve the version, then creates the GitHub release `v<version>` at the run's commit. The actions are pinned at Motherload's commits (`actions/checkout` v7.0.1, `nubjs/setup-nub` v0.6.0 with nub 0.9.6). The workflow `.github/workflows/test.yml` runs the same four checks on every push to `main` and every pull request against it, where `tests/motherload.test.ts` is skipped, since `MOTHERLOAD_DIR` is unset.
- **What differs for one package:** there is no staging order to keep (Motherload stages `@motherload/core` first and `motherload` last), so the `stage` job resolves one name in place of a list and checks the registry once; the step summary's `stager reject` and `stager await` name `dotschema@<version>`; the release notes link the README on GitHub in place of a docs site. The script `scripts/bump.ts` (`nub run bump <version>`) writes the version into the one `package.json`, where Motherload's writes every manifest and the dependencies between them.
- **The environments,** created on 2026-10-21 with `gh api -X PUT repos/colinhacks/dotschema/environments/<name>` and a deployment-branch policy for `main`, match colinhacks/motherload's as read the same day, field by field: `npm` and `release-approval` each have the maintainer (`colinhacks`) as required reviewer, `prevent_self_review` off, no wait timer, custom branch policies with the one branch `main`, and administrators allowed to bypass. The repository's Actions settings are Motherload's too: every action allowed, and the token read-only by default, so each job asks for what it needs (`id-token: write` to stage, `contents: write` to release). Neither repository has a secret or a variable.
- **The manifest** names `repository` (`git+https://github.com/colinhacks/dotschema.git`), `homepage` (the README on GitHub), `bugs` (the issues) and `author`; Motherload's manifests carry `repository` and `author` and neither of the others.
