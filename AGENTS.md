# Agent notes

Read [PLAN.md](./PLAN.md) first: what dotschema is, what the maintainer decided, the steps, and what is open. [DESIGN.md](./DESIGN.md) holds one section per design decision with its alternatives and evidence; a change to a decision updates its section.

The dotschema package types `.schema.jsonc` and `.schema.json5` imports: each becomes the TypeScript type its JSON Schema describes plus a validator compiled by ajv. It is a TypeScript 7.1 content mapper, a preload, and plugins for esbuild, Vite, webpack, Next.js and Jest, taken out of Motherload (`~/Documents/motherload`) on 2026-10-21. Motherload, the data loaders, is its sibling: read its repository, do not write to it. The two share a protocol for loaders in one host, whose global keys are Motherload's ([DESIGN.md](./DESIGN.md#the-shared-protocol)); a change to it is made in both.

## Layout

| Path | What it is |
| --- | --- |
| `src/schema.ts` | The module a schema file becomes: `.validate()` and `.is()`, each with its own ajv standalone validator, inlined with the helpers they require and the files of the formats they use; each definition's validator, a named export; for a plain object, one validator per property, joined at run time, which `.pick()` and `.omit()` reuse; the `contains` guard; the discriminators added to the copy ajv compiles; the types' text |
| `src/schema-types.ts` | The emitter: a JSON Schema as TypeScript declarations |
| `src/formats/` | The formats `format` names ([DESIGN.md](./DESIGN.md#formats)): `index.ts`, the table every ajv dotschema makes registers, each format a regular expression, `true` or a file; and one plain JavaScript file in CommonJS per format checked by a function, whose `module.exports` is the format as ajv's `addFormat` takes it, which a module inlines only when it uses the format: copies of ajv-formats' (MIT, credited in each), with `date-time`, `time`, `duration` and `uuid` fixed where the JSON Schema Test Suite catches them, and dotschema's own `email`, `hostname`, `uri`, `uri-reference` and `regex` in place of ajv-formats' (`uri-template` an expression in the table), and of Zod's checks for its formats (`jwt`, `credit_card`, `iban`, `base64`, `base64url`, `cidrv6`, `currency_code`), Zod's other formats being its regular expressions in the table; and dotschema's own `idn-hostname` (UTS #46's mapping, then IDNA2008's checks with Unicode 17's tables in `idna.cjs`, which `hostname` shares), `idn-email`, and `iri` and `iri-reference` on RFC 3987's grammar in `iri-grammar.cjs`, which builds on RFC 3986's in `uri-grammar.cjs` |
| `src/refs.ts` | The `$ref`s a schema follows into other schema files, and the problems of `$dynamicRef` and of an `$id` below a file's root |
| `src/json-schema.ts` | The schema, or one of its definitions, as one self-contained JSON Schema in draft-07 or 2020-12, for Standard JSON Schema |
| `src/parse.ts` | The two dialects, JSONC and JSON5, read with their positions kept, and the `/** */` comments before their keys, which the types write as JSDoc |

The `package.json` links `dotschema` to the repository itself (`link:.`), because a mapper package does not resolve through self-reference. It is private and points at the TypeScript sources; only `dist/dotschema` is published.

## JavaScript: nub

Prefer `nub` over `node`, `bun`, `npm`, `npx`, `pnpm` and `yarn`: run files with `nub <file>`, package scripts with `nub run <script>`, local CLIs with `nubx <tool>`, installs with `nub install` and `nub add`. The lockfile is `pnpm-lock.yaml`, which nub reads and keeps.

- Running `nub run typecheck` type-checks the sources and runs the content mapper on `lab/basic` (`tsc --runExternalCode`).
- Running `nub run test` runs `tests/**/*.test.ts` with `node --test`. The tests of `lab/bundlers`, `lab/nextjs`, `lab/jest` and `lab/cloudflare` are skipped until `nub install` has run in that lab (`for dir in lab/bundlers lab/nextjs lab/jest lab/cloudflare; do (cd "$dir" && nub install); done`), and those of `lab/bun` where Bun is not installed. With `MOTHERLOAD_DIR` set to a Motherload checkout with its dependencies installed, it also runs the interop tests against it: `MOTHERLOAD_DIR=~/Documents/motherload nub run test`.
- A `NODE_COMPAT=1` in the environment, which nub's `node` shim passes on, makes `nub` run as plain Node and read no `nub.jsonc`; the tests unset it for every command they run (`env` in `tests/helpers.ts`), and a command run by hand in `lab/nub` needs it unset or `0`.
- Running `nub run build` writes `dist/`, and `nub run check-dist` then installs it outside the repository and runs it, with the newest version in each dependency's range; `nub run check-dist --lowest` runs it with the oldest. The dependencies are caret ranges on the oldest versions that pass the checks ([DESIGN.md](./DESIGN.md#packaging)): to run the repository's own checks at those, add an `overrides` field naming each floor to `package.json` and run `nub install`, then take the field out, run `git checkout pnpm-lock.yaml` and `nub install` again, so the lockfile keeps the newest.
- Setting `TS_CONTENT_MAPPER_DEBUG=1` on `nubx tsc -p lab/basic/tsconfig.json --noEmit --runExternalCode` prints the JSON-RPC traffic.
- The nub installer refuses a package version younger than 24 hours (`minimumReleaseAge`); the TypeScript nightly is pinned to the one Motherload pins. Do not bypass the gate.

## Git

Work lands on `main` directly, with no branch or pull request. When a task is done and `nub run typecheck` and `nub run test` pass, commit it to `main` and push it to `origin`, colinhacks/dotschema, public on GitHub since 2026-10-21. Several sessions can work in this checkout at once, so stage only the files the task changed. A commit message is one prose paragraph: what changed, why (quoting the maintainer where the maintainer asked for it), and what was verified.

A release is never cut by a push: run `nub run bump <version>`, commit and push it, then `gh workflow run release.yml -R colinhacks/dotschema`, approve the run's `npm` deployment, and ask the maintainer to run `stager` in a terminal, which approves the staged version under one authenticator code and resumes the run ([DESIGN.md](./DESIGN.md#releasing)). After the approval, `stager --list` should show nothing of the release left staged. If the held run is still waiting once npm serves the version, `stager resume colinhacks/dotschema <version>` resumes it, as it did for 0.0.1, the first release, on 2026-10-26.

## Writing conventions

The product is dotschema, lowercase, in prose; `dotschema` in code is the package, the import specifier, the diagnostic source and the Standard Schema vendor. Never hard-wrap Markdown: every paragraph, list item and table row is one line. Write a method with its dot and parentheses, `.is()` and `.validate()`, never a bare `is`. Never open a sentence with inline code: a word that names the thing leads, as in "The `$schema` keyword picks the draft". In the README, show a behavior as an example, a sentence that leads into its own code block, one fact to each example (the maintainer, 2026-10-21: "It's just one piece of information at a time, always."), and leave out what a reader does not need: an edge case, a rule ajv or TypeScript already enforces, a reason behind a name. Never put three paragraphs in a row, and never a list of dense rules with code inline in place of examples (the maintainer, 2026-10-21, of such a list in Motherload's docs: "not acceptable. It's just not even needed ... Just break up that section into a series of examples with different code blocks ... The vast majority of that does not need to be stated"). A fact the README leaves out stays in DESIGN.md. Never estimate developer time. Anything stated as fact traces to a file read or a command run; a guess goes in PLAN.md's Open section as a question.
